# TaskHub V2 前端设计规范

## 1. 产品定位

TaskHub V2 前端是 AI 软件交付控制台，不是聊天界面。它需要让操作者在一个工作区内完成三类核心工作：

1. 识别需要关注的任务，并快速进入处置。
2. 创建项目与交付任务，观察 LangGraph 工作流的实时状态和证据。
3. 检查模型、执行节点、验收能力及预生产环境是否满足运行条件。

设计关键词为：**可信、克制、清晰、高密度**。视觉上采用现代项目管理工具的轻盈感，同时保留企业控制台对状态、证据和异常信息的表达能力。

## 2. 设计原则

### 状态优先

页面首先回答“系统是否健康、哪些任务需要我处理、流程停在哪里”。状态不能只依赖颜色，必须同时提供文字。运行中、待人工、阻塞、失败和完成使用稳定且全站一致的语义色。

### 渐进披露

任务列表呈现决策所需的最少字段；任务详情先展示流程和待办，再展示证据；系统配置通过分组面板按需展开。低频配置不与日常任务争夺视觉注意力。

### 证据可追溯

规划、代码、测试、验收、模型调用、发布和时间线统一归入“交付证据”。编号、提交、节点、来源与哈希使用等宽字体，便于核验和复制。

### 安全操作

主要操作每个区域只保留一个。拒绝、终止、停用等破坏性操作不得使用主色；阻塞恢复操作必须在原因、责任节点和建议操作之后出现。

### 渐进式工程演进

当前版本保留原生 HTML/CSS/JavaScript 和既有 DOM ID/API 契约，避免 UI 重构影响交付流程。后续复杂度达到迁移阈值后，再将相同信息架构迁移到 React + TypeScript。

## 3. 信息架构

| 一级区域 | 用户目标 | 核心内容 |
| --- | --- | --- |
| 任务中心 | 找到并处置工作 | 筛选、状态、当前环节、阻塞原因、更新时间 |
| 开发流程 | 发起和跟踪交付 | 项目、需求、流程图、人工动作、交付证据 |
| 系统配置 | 建立单 Seed 控制面与本机节点 | Seed 状态、TaskHub 节点；模型和平台高级设置 |

桌面端使用顶部全局栏 + 左侧固定导航 + 主内容区。窄屏仍保持导航与内容的空间关系；在更小的手机屏幕上，导航变成顶部横向标签。

左侧一级菜单使用独立的导航按钮样式，不复用页面内的主按钮或次按钮样式。三个入口的默认状态完全一致，仅当前页面增加品牌色背景、边框和图标颜色。

任务中心、开发流程和系统配置共享同一个一级页面骨架：相同的标题基线、说明文字、页头高度、右侧操作区及页头到首个内容卡片的距离。业务组件可以不同，但不得各自定义页面级间距。

## 4. 页面规范

### 4.0 登录与首次设置

- 启用密码登录的部署首次访问时显示“设置管理员密码”，不显示普通登录框。
- 首次设置必须提交部署生成的初始化口令、新密码和确认密码；新密码至少 10 个字符。
- 设置成功后立即建立管理员会话。初始化口令仅用于首次身份确认，不作为后续日常登录密码。
- 后续访问只显示管理员密码输入框，不在页面暴露初始化口令或密码哈希。
- 登录和设置使用同一登录卡片、状态区域、键盘 Enter 操作与移动端 16px 输入字号规则。
- 密码设置完成后，如果服务端就绪判定尚未通过，自动进入 Seed 首次启动向导；用户可以在当前会话选择稍后配置。
- 首次启动向导使用状态清单连接现有系统配置表单，不复制平台、模型、主机或节点配置表单。
- 每一步同时显示编号/完成符号、文字状态、诊断摘要和下一步动作；全部完成时明确显示“系统已具备运行任务条件”。
- 向导直接展示 Docker Engine CPU、内存和 TaskHub 持久化磁盘容量，并提供离线工作镜像导入与等待配置生效时的 Seed 重启入口。
- 登录页只承担管理员认证和首次密码设置，不呈现镜像下载信息。公开镜像地址保留在登录后的系统配置页，并由版本化部署文档和发布页面同步提供。
- 日常登录同时输入用户名和密码；页头显示当前用户名与角色。会话超时后回到登录卡并明确提示，不保留密码字段。

### 4.1 全局栏

- 左侧展示 TaskHub 产品标识和“AI 交付控制台”定位。
- 右侧只放全局服务状态和退出操作。
- 服务状态必须有状态点与文本，不以装饰性图标替代诊断结果。

### 4.2 任务中心

- 页头由标题、说明、任务总量和刷新操作组成。
- 异常处置中心位于筛选器之前，只投影服务端检查点和任务索引中的等待、阻塞与失败状态，不维护第二套流程状态。卡片明确显示分类、严重度、原因与建议动作；点击后进入任务详情并复用该检查点已有的恢复选择。
- 交付证据中心紧随异常处置，按任务汇总实施、验收、监督与发布四段来源链路，并显示测试通过数、证据通过数、流程完整度、制品摘要完整性和明确缺口。它只读投影检查点，不允许在汇总卡片中改写证据。
- 实施、验收和发布等规范阶段筛选必须包含对应的 blocked 子状态，避免异常任务从筛选结果中消失。
- 筛选区是独立工具栏，输入框应有可见标签或辅助文本。
- 表格行整体可点击，并支持键盘 Enter 打开。
- “待办 / 阻塞原因”是最高价值字段，异常状态提高对比度。
- “任务”超过 15 个字符、“待办 / 阻塞原因”超过 20 个字符时默认截断；“展开 / 收起”按钮紧跟在截断文字末尾，查看全文时不得触发进入任务详情。
- 任务表格为“项目”和“当前环节”保留固定的单行列宽；空间不足时表格区域横向滚动，不得把这两个字段挤压换行。
- 分页与总量相邻，避免用户在表格上下文之外寻找导航。

### 4.3 开发流程

- 项目上下文和“新建 / 接入”动作位于工作区顶部。
- 启用产品化编排后，开发需求先生成 ProductSpec 草稿，不直接启动实施。产品规格卡展示原始需求与结构化目标、范围、用户、功能、非功能、交付、验收、风险和假设的对应关系。
- 产品规格卡同时承担版本呈现和治理入口：集中解决一次产品级待决策事项，再提交评审和批准；批准版本不可编辑，需求变化创建引用上一版本和变更原因的新草稿，并可查看字段级差异。
- “开始流程”只有在当前项目存在已批准 ProductSpec 时才创建运行，并将运行永久绑定到明确的规格编号和版本；功能开关关闭时保持现有线性流程兼容行为。
- 代码仓库是当前项目的持久配置，位于项目上下文下方并使用对象卡同时呈现仓库类型、认证方式、远端、基准分支和控制中心工作副本。普通开发人员和审计人员可查看，项目负责人和管理员可修改、保存及测试连接。
- Git 远端地址不得嵌入密码或访问令牌。SSH 仓库使用 Seed 的运行身份；界面不回显凭据。保存必须验证本地仓库、基准分支和远端分支，并在失败时恢复原配置。
- Git 模式启动任务前必须重新检查项目仓库；仓库、基准分支或远端不可用时，在创建运行之前明确阻止流程。
- 项目页在创建/接入区之后固定展示服务端项目预检中心。预检统一汇总代码仓库、模型服务、Seed 本机执行能力、项目契约、质量命令和验收依赖；阻塞项提供明确修复入口，“开始流程”只在预检通过后启用。页面不得自行复制这些就绪规则。
- 新任务表单使用卡片容器，需求输入是主要字段，“开始流程”是唯一主操作。
- 新任务表单不展示“生产线”输入；内部继续提交 `default` 以兼容既有 API、索引和历史任务。生产线在形成明确的多流水线业务模型前，不作为用户配置项。
- 开发需求文本框独占整行；状态提示和“开始流程”组成独立底部操作栏，桌面端按钮右对齐，手机端按钮占满可用宽度。
- 工作流节点按交付顺序呈现，节点同时显示序号、名称和状态。
- 人工待办和阻塞面板置于证据之前，并用语义色与普通信息分离。
- 证据默认折叠；摘要必须让用户无需展开即可判断是否完整。
- 执行记录与其他证据栏目使用相同的正文、字号、行高和内容内边距；时间线仅改变内容排列，不建立独立字体体系。

### 4.4 系统配置

- 配置页定位为全局控制面与运行资源管理，不接纳项目专属配置。
- 每个资源分组在折叠标题中显示健康摘要。
- 一级分组固定为 Seed 状态、TaskHub 节点、模型服务和高级设置；前两项构成主要配置流程，后两项使用次级视觉层级。
- Seed 状态使用紧凑的角色就绪卡片，不使用横跨整页的稀疏诊断表。固定展示 Seed 控制、执行、测试、预生产四类角色；每类只核验自身通用必备环境，并区分尚未部署、节点离线、能力缺失和环境就绪。
- TaskHub 节点和高级设置沿用 Seed 状态的卡片语言：每个 Agent/节点容器和每组平台状态独立成卡，卡头表达身份与状态，卡体表达关键事实，卡尾承载对象操作。
- 节点创建和可管理平台参数按业务主题拆成配置卡片。诊断、备份和审计仍放在二级折叠中，不把全部表单长期平铺。
- Seed 控制节点通用必备项为 Docker Engine、CPU、内存和持久化磁盘；执行节点为 Git、Python 3、编码执行器和工作区写入沙箱；测试节点与预生产节点为 Git、Python 3 和 pytest。Node.js、浏览器、测试数据库等项目特有能力继续按项目任务契约核验，不作为所有节点的统一硬门槛。
- 一级分组采用单开手风琴：同时只展开一项，切换栏目时自动收起上一项；首次进入默认展开 Seed 状态，并记住用户最近展开的一级栏目。
- 一级折叠标题是系统配置的主导航行：使用固定序号、15px 栏目名、12px 职责说明、独立健康摘要胶囊和有边界的展开按钮；展开项以左侧品牌色标记，关闭项也必须保持完整可辨识的行轮廓。
- 展开的一级标题在滚动时吸附于全局栏下方；离开标题原始位置后显示“收起当前项”快捷按钮，使长内容无需返回顶部即可关闭。
- 日常状态和资源清单直接显示；新增表单、可管理参数、资源负载、能力前置和操作审计使用二级折叠按需展示。二级折叠不改变一级健康摘要。
- 二级折叠以带圆角和完整边框的功能卡呈现，不再伪装成表格分隔行；对象卡和配置卡统一采用 14px 标题、12px 说明/标签、13px 事实值的层级，等宽技术值使用 12px。
- 刷新动作属于分组；预生产验收属于当前项目设置，并位于开发流程的项目上下文。
- 开发流程页头提供唯一的“当前项目”选择器，运行创建与预生产验收配置共同跟随该选择，不在配置卡内重复选择项目。预生产验收默认关闭，普通开发、单元测试和临时浏览器预览无需填写；启用后仅将完整预生产访问 URL 作为必填项。入口网关主机和应用服务主机仅作为自定义部署/验收脚本的高级可选环境变量，入口未填时从访问 URL 自动识别。
- 项目必须从“创建 Git 仓库”或“接入 Git 仓库”开始。两种方式都要求操作者确认完整远端地址和 Seed 控制中心工作副本位置；发现列表只用于填充建议值，不能替代这两个必填字段。服务端限制远端位于配置的权威 Git 根目录、工作副本位于托管项目根目录，并在创建或克隆前拒绝越界位置。
- Git 仓库服务属于全局平台配置，不在每个项目中重复维护。管理员在“高级设置 → 可管理平台参数”配置 SSH 用户与主机、端口、权威裸仓库根目录、Seed 工作副本根目录和可选私钥；私钥只显示配置状态并加密保存。连接测试可使用尚未保存的表单值。创建和接入项目表单显示当前服务摘要并提供直达配置入口；发现失败时保留错误提示和手工远端填写能力。
- 命令、错误原因和修复建议允许换行，不截断关键证据。
- 执行节点、节点容器、节点负载和节点验收前置统一归入“工作节点”，分别表达调度、容器、资源和能力状态。
- 启用容器管理的 Seed 在“工作节点”中创建、启动、停止和移除执行、测试、预生产节点；所有节点固定运行于 Seed 本机 Docker，不提供目标主机选择。
- 容器操作结果写入可访问的状态区域；移除前必须确认，并明确默认保留节点数据卷。
- 产品不提供物理主机库存、SSH 准入、跨主机部署、迁移重建、远程镜像升级或远程凭据操作。旧数据仅为升级兼容与审计保留，不进入当前交互流程。
- 工作节点的“日志与诊断”作为二级披露，按节点聚合 Agent 事件、容器最近日志、Docker 操作、最后错误、CPU/内存/磁盘和槽位占用。一键诊断包必须脱敏，不得包含环境文件、令牌、私钥、模型账号或数据库转储。
- 模型服务在配置卡之后提供只读运行运营面板，合并服务健康/熔断状态、可用额度信息和最近任务检查点中的调用次数、平均耗时与回退次数；运营查询失败不得阻断模型卡配置、保存或连接测试。
- 备份与恢复保持主机侧操作，不通过浏览器传输敏感备份。Linux 与 Windows 备份完成前都必须运行只读验证；验证覆盖文件摘要、配置主密钥身份、PostgreSQL 身份记录和数据归档，并可在恢复前独立复验。
- 能力包库存卡片的标题、事实字段和摘要正文使用一致的 15px 内容内边距，避免字段和值贴近卡片左边界；手机端仍保持同一张卡片内部对齐线。
- Seed 按心跳周期协调本机容器期望状态和 Agent 健康状态。失联节点必须自动退出调度，容器和 Agent 恢复且身份、健康验证通过后才重新纳管；重复协调不得创建重复容器或数据卷。
- 模型服务使用可增删的紧凑模型信息卡片，不再保留独立模型资源列表或按供应商堆叠固定大表单。卡片是模型状态呈现与配置的唯一载体，直接显示名称、服务商、认证模式、API 地址、模型、代理、启用状态、凭据状态和角色路由；所有输入控件保持统一高度。
- OpenAI 模型卡片可选择 API 或 ChatGPT 账号认证。账号认证由控制器启动 `codex login --device-auth`，前端展示登录地址和设备验证码并轮询结果；令牌文件只保存在 Seed 持久化配置目录，不写入数据库、响应或日志。
- 设备授权优先使用当前模型卡片的网络代理，未填写时再使用 Seed 全局 OpenAI 代理。20 秒内未取得验证码时必须结束子进程并显示网络、代理与设备码权限检查提示，不能无限停留在“正在请求设备验证码”；验证码签发后等待用户完成授权的上限为 15 分钟。
- 设备授权状态区只展示 Codex CLI 实际返回的登录地址和验证码，不在浏览器中预设地址或生成验证码。返回前显示“等待 Codex CLI 返回登录地址和验证码”，返回后原位展示二者；后端按输出块而非按行解析，兼容 CLI 未输出换行符的情况。
- 设备码解析兼容 Codex CLI 当前的分段字母数字格式，不假定每段固定为四位；ANSI 终端颜色码必须先剥离，并且只从 “one-time code” 提示后的值或独占行提取，不能把 `COMMAND-LINE` 等 CLI 标签识别成验证码。
- 模型账号授权目标固定为 Seed 控制器的模型账户，不向工作节点分发账号令牌。每次点击“生成新的登录验证码”都终止同模型的旧 Codex CLI 会话并创建新会话；页面显示 Seed 和模型 ID，旧轮询不能覆盖新会话。
- 设备验证码末尾提供就地复制按钮，成功或失败都在按钮上显示文字反馈；剪贴板 API 不可用时使用浏览器兼容复制方式，用户无需手工选择验证码。
- 每张模型卡片可承担规划、编码、监督、评审和风险分析角色。主备关系按角色独立配置：一个主模型、按数字排序的多个备用模型；同一模型可在不同角色中使用不同优先级。
- 同时启用多张模型卡片时，页面在提交前检查五个角色是否各有一个主模型，以及同角色的主备顺序是否唯一；不完整或冲突的路由必须以中文列出具体角色，不能只显示通用 422 错误。
- 每张模型卡片的“测试并读取模型”使用当前表单中的地址、代理和临时 API Key 验证连接，无需预先保存或填写模型名；API Key 只用于本次测试且不持久化。API 模式读取兼容服务的 `/models`。新建 ChatGPT 账号卡片也可在保存前启动该卡片独立 `CODEX_HOME` 的设备授权，授权成功后直接读取 Codex CLI 模型目录，且不能因刷新服务端配置而丢失未保存卡片。结果在原卡片内以下拉列表呈现，选择后填入模型字段，再完成保存。
- 模型连接测试按服务商选择协议适配器，不能将所有服务硬套 OpenAI `/models`。MiniMax 使用国内/国际站官方认证接口，并在认证成功后提供官方文本模型目录；含空白字符的 Key 在请求前给出明确格式错误。
- 模型卡片底部在宽屏采用左右两栏：压缩后的角色与主备顺序位于左侧，连接测试、删除和就地状态位于右侧；900px 以下卡片及底部内容恢复单列。
- 模型主路由连续发生 3 次服务故障后才熔断；主模型恢复期每 30 秒允许一次探测，连续 3 次成功后仅让新任务恢复主模型。切换后至少保持 5 分钟，限流、超时、网络和服务端故障参与判断，权限、参数和业务内容错误不触发持续熔断。
- 平台设置允许管理 Seed/Agent 地址、节点镜像、默认资源、心跳和保留策略，同时明确区分 Web 管理配置和不可回读的启动根配置。
- 平台设置的 Seed 对外地址与 Node Agent 回连地址在桌面及中等宽度下并列呈现，仅在手机宽度改为单列，避免短地址卡因同排卡片高度产生大面积空白。
- 平台设置中的私有仓库和国内代理使用 Docker 镜像前缀格式，不填写 URL scheme。仓库密码只允许替换，页面只显示脱敏配置状态。
- Seed 备份恢复说明位于平台设置二级披露。正式脚本备份 PostgreSQL、TaskHub 数据卷、部署配置和镜像；恢复必须在破坏性操作前后验证文件校验和及加密主密钥—数据库身份匹配。敏感业务备份不通过 Web 下载。
- 用户、权限与访问安全位于平台设置二级披露。管理员可创建、停用、更新或删除项目负责人、开发人员、只读审计人员和其他管理员，并可轮换会话签名密钥；内置管理员不可删除，密码哈希与令牌不回显。
- 非管理员仍可只读查看其权限范围内的运行资源；无权限表单不呈现，服务端必须独立执行相同权限判断，不能依赖前端隐藏。
- 配置保存后同时展示期望版本和生效状态；需要重启时明确提示，并在模块内展示不含密钥原文的最近操作审计。
- Seed 本机节点只加入 TaskHub 内部网络。远程 Alpha 节点发布受令牌保护的 Agent 端口供 Seed 访问；该端口必须由可信内网或主机防火墙隔离。预生产节点是构建/测试/验收运行资源，项目的实际预生产访问地址由开发流程中的项目设置管理。

## 5. 视觉系统

### 色彩

| Token | 用途 |
| --- | --- |
| `--accent` | 主操作、当前导航、品牌焦点 |
| `--success` | 完成、可用、通过 |
| `--warning` | 待人工、需注意 |
| `--danger` | 阻塞、失败、破坏性动作 |
| `--info` | 运行中、当前流程节点 |
| `--surface` | 主卡片 |
| `--surface-subtle` | 次级区域、表头、禁用区 |

正文与背景对比度以 WCAG AA 为最低目标。大面积背景使用中性灰，品牌绿色只用于焦点和动作，避免整页泛绿。

### 字体与尺寸

- 使用系统无衬线字体，中文优先 `PingFang SC` / `Microsoft YaHei`。
- 页面标题 24px，区块标题 16–18px，正文 14px，辅助信息 12px。
- 基础间距单位 4px，常用间距为 8 / 12 / 16 / 24 / 32px。
- 控件最小高度 38px；触摸环境的关键操作最小高度 44px。

### 容器

- 卡片圆角 12px，边框比阴影更重要。
- 阴影只用于全局栏、登录面板和需要浮层感的区域。
- 表格、资源列表和证据列表共享边框、分隔线与悬停反馈。

## 6. 交互与可访问性

- 所有可点击表格行支持键盘焦点，并显示 `focus-visible` 轮廓。
- 表单输入必须关联 `label`，图标按钮必须有 `aria-label`。
- 状态变化写入现有 `role="status"` 区域。
- 加载中的按钮禁用并保留文字反馈，禁止只显示无限动画。
- 窄屏输入控件使用不小于 16px 的实际字号，防止移动端浏览器聚焦时自动放大页面；不得通过禁用用户缩放规避此问题。
- 动画只用于 150–200ms 的颜色、边框和位移反馈；尊重 `prefers-reduced-motion`。
- 桌面优先支持 1280–1600px；680px 保持关键验收用例；小于 560px 时允许表格横向滚动。

## 7. 前端工程边界

### 标准镜像交付边界

- 正式发布使用 `deploy/release/compose.yaml`，不得携带快速开发源码挂载。
- 用户只接触 Seed、统一 Node 与 PostgreSQL 三个镜像；Node 的执行、测试、预生产角色由容器启动配置限制，不复制角色镜像。
- 在线和离线初始化共享同一 Compose 与配置结构。离线包必须包含镜像 ID 清单和 SHA-256 校验，且按 CPU 架构分别生成。
- Linux 初始化只接受已经可直接使用的 Docker 用户权限，不在 Web 或脚本中收集 sudo 密码。
- 升级前备份 TaskHub 数据卷、PostgreSQL、部署配置和旧镜像；恢复操作只能覆盖固定命名的 TaskHub 数据卷。

### 当前重构范围

- 保留 FastAPI 静态文件交付方式。
- 保留所有 API、事件流、DOM ID 和业务事件处理。
- 建立 CSS token、页面壳层、卡片、状态、表格、表单和响应式规范。
- 对现有页面进行语义化分组与无障碍补强。

### React 迁移触发条件

满足任意两项时启动独立 `taskhub-web`：

- 页面数量超过 6 个，或出现三级路由。
- 多个页面共享复杂的可编辑状态。
- 工作流需要缩放、拖拽或大型拓扑可视化。
- 前端单元测试和组件复用收益明显高于构建链成本。

建议技术栈为 React、TypeScript、Vite、TanStack Query/Table、React Flow、Monaco Editor，并以当前 API 作为稳定边界。组件视觉可参考 shadcn/ui，但 TaskHub 自己维护 token 和业务组件，避免把组件库结构直接暴露给业务代码。

## 9. 验收标准

- 登录、任务筛选、任务打开、异常恢复、项目创建/接入及资源检测功能不回归。
- 1440px 桌面端导航与内容无重叠，任务表格可完整阅读。
- 680px 验收视口中侧栏仍位于内容左侧；手机视口不产生页面级横向溢出（表格容器除外）。
- 状态不仅通过颜色表达；键盘可访问主导航、任务行、表单和操作按钮。
- 页面不加载外部字体、图标或运行时依赖，可在内网环境完整使用。

## 10. 自动推进与人工处置

- 开发运行采用九阶段视图：需求、规划、实施、验收、审查、风险、监督、发布、完成。
- 规划产出后直接进入实施，监督结论为通过时直接进入发布；页面不再呈现“计划审批”或“发布审批”卡片、筛选项与按钮。
- 人工操作只用于有实际决策价值的状态，例如实施/验收/发布失败、证据缺失、修订次数达到上限、项目重绑定或取消任务。
- 历史 `plan_approval` 与 `merge_approval` 检查点由服务启动恢复逻辑自动放行，不重新暴露为正常用户流程。
# Phase 2 项目契约界面补充

- “项目契约”与“产品规格”是开发流程中的同级折叠栏目，统一使用既有管理卡片标题、状态徽标、12/13/14px 字阶和 9px 内层圆角。
- 契约卡片同时承担配置与呈现：模板、技术栈、模块数、质量命令、机器文档和审批信息不得再拆成稀疏大表格。
- 宽屏事实卡采用两列，680px 及以下降为单列；长契约编号、提交摘要和审批信息必须允许换行，不得产生页面横向滚动。
- 生命周期按钮只显示当前状态可执行的动作；契约门禁结果在卡片内就地呈现，不使用弹窗或独立列表页。
- 功能开关关闭时隐藏产品规格和项目契约栏目，保留旧线性流程兼容行为。

# Phase 3 执行计划界面补充

- “执行计划与动态批次”是开发流程中的只读同级折叠栏目，只在产品化功能开启且当前运行已生成服务端计划时显示。
- 默认使用可读的文本卡片，不在原生前端伪造 DAG 图。计划事实使用四列桌面卡；批次和任务使用两列桌面卡，680px 及以下统一单列。
- 卡片严格使用 14px 标题、13px 事实/正文、12px 编号/标签/等待原因；状态必须同时显示文字，不能仅依赖颜色。
- 每个任务呈现任务标题、稳定编号、状态、依赖、分配节点、资源锁和等待原因；每个批次呈现顺序、状态、任务和实际节点分配。
- 视觉数据只来自 `/api/runs/{run_id}/execution-plan`，SSE 更新运行时重新加载服务端视图；界面不在浏览器内推导 DAG、Ready 或批次。
- 静态资源版本为 `styles.css?v=42`、`app.js?v=16`。真实 Chrome 的 1440、680、390 像素回归覆盖列数、字体和页面级横向溢出。

# Phase 3A 项目生产画布

- 生产画布位于独立 `/canvas/` 路由，由 `taskhub-web` 的 React、TypeScript、Vite、React Flow 和 TanStack Query 实现；任务中心、开发流程和系统配置继续使用现有静态前端，直至逐页达到能力等价。
- 画布分离长期生产拓扑与最新交付运行叠加层。布局、绑定和类型连线只写入草稿；必须先保存、服务端校验再激活，不能由拖拽直接改变生产调度。
- 节点卡使用与运行概览一致的紧凑事实层次，明确显示角色、名称、绑定资源、健康和槽位。运行叠加层显示最新运行阶段、任务数、健康节点与槽位占用，不在浏览器推导 DAG 或节点资格。
- 桌面端提供拖线、框选、拖拽、缩放、平移、小地图、自动布局、撤销/重做和上下文菜单；工具栏、Shift+F10 与节点/连线列表是等价入口。资源绑定使用服务端节点库存选项，资源池允许多选成员。
- 从画布上下文菜单新建节点时，浏览器屏幕落点必须转换为当前缩放和平移后的画布坐标，使节点立即出现在操作位置。空画布或只读版本上的添加操作先自动创建或切换到草稿，再在同一次操作中添加节点；保存、校验与激活仍遵循草稿生命周期。
- 760px 以下变为单列，画布保持查看能力，完整节点绑定、连线语义修改和删除操作保留在列表视图。1440、680、390px 都不得产生页面级横向溢出。
- 画布使用同源认证、CSRF 和 API；FastAPI 只提供构建产物，Dockerfile 在 Python 安装前构建前端。旧开发流程入口为“打开生产画布”。
- `/canvas/` 入口 HTML 禁止浏览器缓存，确保每次加载都获得当前带内容哈希的 JS/CSS 引用；带哈希的静态资源仍由静态服务处理。增量镜像必须覆盖 Python 实际安装包中的画布资源，不能只更新构建源码目录。

# Phase 4 变更与持续修订

- 变更请求位于开发流程中的同级折叠栏目，采用既有管理卡片、状态文字和 14/13/12px 字阶；当前静态资源为 `styles.css?v=44`、`app.js?v=17`、`revision-center.js?v=1`。
- 浏览器只提交变更原因、路径和可选任务，不自行推导影响。受影响子图、复用任务、回归范围、计划版本和审批状态全部来自服务端。
- 卡片同时承担配置与呈现：桌面两列，680px 及以下单列；长任务 ID 和路径可换行，不产生页面级横向滚动。
- “重新执行”和“复用成果”必须并列展示；状态同时使用文字和颜色。批准、应用、拒绝动作只按服务端生命周期和 `delivery:execute` 权限出现。
- 应用变更不得覆盖历史 attempt；新计划中的复用 attempt 必须明确引用原 attempt，页面也不得将其表现为重新执行。

# Phase 5 设计与能力包

- “设计与能力包”是开发流程中的同级折叠栏目，项目选择、当前锁、升级迁移和设计合同在同一紧凑卡片面呈现；平台级导入、信任和停用属于系统配置“平台设置”下的二级库存卡片。
- 推荐方案最多三个，只显示服务端判定兼容的受信组合。浏览器不得自行拼装兼容矩阵；每张方案卡同时显示用途、四类精确版本和登录、列表、详情、移动端四个代表性预览。
- 当前锁必须明确显示 ProductSpec 版本。规格修订后旧锁显示“需重新锁定”；升级先显示迁移任务和待激活状态，不能把选择按钮直接表现为已生效。
- 桌面宽屏使用三列推荐，681–1100px 使用两列，680px 及以下单列；合同事实为四列并在窄屏降为两列。标题、事实和辅助信息继续使用 14/13/12px，长版本引用允许换行。
- 能力包状态必须以“待审查、受信可用、已停用、待激活、已锁定”等文字表达。可执行包必须在卡片内单独确认权限审查，不使用无上下文确认弹窗。
- 当前静态资源为 `styles.css?v=45`、`app.js?v=18`、`capability-center.js?v=1`；真实 Chrome 1440、680、390 像素覆盖选择、激活、库存和页面级横向溢出。

# Phase 6 规模化运行策略与执行分析

- “运行策略”是开发流程的项目级配置/呈现卡片，只允许配置并发任务上限、优先级权重和
  单次运行成本预算。卡片必须说明策略只冻结到之后的新计划，不能暗示会修改历史运行。
- 执行计划事实、预测和瓶颈全部来自服务端。浏览器不得自行计算关键路径、Ready、成本或
  证据完整率；分析卡使用 14px 标题、13px 值和 12px 标签/说明。
- 任务文本视图每页最多 100 项，显示当前范围、总数、页码和上一页/下一页。翻页只替换
  任务卡，不隐藏全图预测和动态批次。
- 宽屏运行策略为三列，预测事实为三列并与瓶颈卡并排；680px 及以下全部降为单列。长锁、
  等待原因和任务 ID 允许卡内换行，不产生页面级横向滚动。
- React `taskhub-web` 继续独占生产画布的复杂共享编辑状态。其余控制台只在完整路由达到
  API、权限、响应式和无障碍能力等价后迁移；不长期维护两套可编辑 DAG 或调度逻辑。
- 当前静态资源为 `styles.css?v=48`、`app.js?v=20`、`resource-center.js?v=26`。
