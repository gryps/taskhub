# TaskHub V2 产品化交付与持续编排 PRD

状态：核心源代码实施完成（Phase 0–6）

版本：1.1

更新日期：2026-09-12

目标版本：TaskHub V2 下一阶段

## 1. 文档目的

本文定义 TaskHub V2 从“单次 AI 开发工作流”升级为“持久化软件生产控制系统”所需的核心产品能力。

用户只需要选择项目并输入软件需求。TaskHub 负责将原始需求产品化为版本化产品规格，将规格编译为具有依赖关系的任务图，根据节点能力和资源冲突动态组织并行批次，持续执行开发、测试、集成、验收和修订，最终形成可发布、可追溯的软件成果。

本文同时定义可组合能力包机制。前端设计、项目结构、测试、安全和交付规范不再只依赖提示词，而是以版本化能力包进入产品规格、任务上下文和自动验收。

## 2. 背景与现状

TaskHub V2 已具备以下基础：

- LangGraph 持久化工作流、暂停、恢复和人工审批；
- 受控 Git 工作区、提交、评审、发布和证据；
- 本地及远程工作节点、能力检测、槽位调度和故障转移；
- 编码、测试、验收和预生产工作负载；
- 模型角色路由、主备切换和账号/API 认证；
- 项目仓库、预生产环境和项目级执行命令；
- 节点凭据、运行审计、诊断、备份和正式镜像交付。

当前主要缺口不是计算节点数量，而是缺少位于工作流上层的稳定生产模型：

1. 原始需求没有被固化为结构化、版本化的产品事实来源；
2. 开发步骤主要表现为线性流程，不能表达复杂依赖和真正的并行批次；
3. 任务缺少统一的输入、输出、修改边界和可执行验收合同；
4. 需求变化、验证失败和集成冲突尚未形成统一的计划修订机制；
5. 项目结构和设计规范主要依赖自然语言指导，缺少机器可执行的架构门禁；
6. 前端风格、组件、布局和品牌能力尚不能作为可选择、可锁定、可验证的产品能力包。

## 3. 产品愿景

TaskHub V2 是 AI 软件交付控制面，不是聊天式代码生成器。

目标工作方式为：

```text
自然语言需求
  -> 需求澄清与产品化
  -> 版本化 ProductSpec
  -> 编译任务依赖图 DAG
  -> 动态计算可执行批次
  -> 调度多个工作节点并行实施
  -> 自动验证与受控集成
  -> 失败时生成修订计划
  -> 人工治理与发布
  -> 保留完整交付证据
```

产品的核心承诺是：同一份已批准产品规格，在相同能力包和项目契约下，能够被暂停、恢复、重新调度和审计，而不会因控制器重启、节点变化或模型切换丢失执行上下文。

## 4. 目标与非目标

### 4.1 产品目标

1. 将用户输入转换为可评审、可版本化的产品规格。
2. 将产品规格转换为带依赖、资源边界和验收合同的任务 DAG。
3. 根据任务依赖、文件冲突、节点能力和可用槽位动态并行执行。
4. 保证每个任务都产生代码、测试、制品和 Git 等结构化证据。
5. 支持需求变更、失败修订、重新规划和增量回归，不覆盖历史事实。
6. 通过项目结构契约保持代码库的一体化和可维护性。
7. 通过版本化能力包为不同项目选择前端设计及其他专业能力。
8. 保持现有项目、运行、认证、节点、Git 和发布能力向后兼容。

### 4.2 非目标

- 不允许 TaskHub 维护人员绕过工作流直接修改受管项目；
- 不以增加任意 Prompt 或无限 Agent 数量替代工程约束；
- 不允许能力包任意执行未声明脚本或访问平台凭据；
- 不在本阶段建设开放互联网插件市场和付费结算；
- 不要求所有项目采用同一种语言、框架或目录结构；
- 不自动发布未经项目策略要求之人工批准的生产版本；
- 不用批次号代替任务依赖图，批次始终是 DAG 的动态调度结果。

## 5. 用户角色与核心场景

| 角色 | 核心诉求 |
| --- | --- |
| 项目负责人 | 输入需求、确认产品规格和能力包、处理产品级决策与异常恢复 |
| 开发人员 | 查看任务边界、技术计划、失败原因和集成结果，发起或恢复交付 |
| 平台管理员 | 管理模型、节点、能力包来源、资源策略、安全和运行健康 |
| 只读审计人员 | 查看规格版本、计划变化、模型调用、代码、测试、制品和发布证据 |
| TaskHub 执行节点 | 消费可执行工作包，返回结构化结果，不自行改变全局产品目标 |

核心场景：

1. 用户输入一个完整软件需求，确认产品化结果后自动持续开发直至发布候选完成；
2. 一个产品规格被拆成多个无依赖任务，由多个节点并行完成；
3. 某任务失败后只修订受影响任务，不重复执行无关成功任务；
4. 用户追加需求，系统生成新规格版本、影响分析和增量 DAG；
5. 用户为前端项目选择风格、组件、布局和品牌包，并在整个项目中保持一致；
6. 控制器或节点重启后，系统恢复到相同任务尝试和调度状态；
7. 审计人员能够解释“为什么生成这个任务、由谁执行、依据什么判定完成”。

## 6. 核心概念

### 6.1 Requirement

用户提交的原始需求及附件。原文永久保留，只允许追加补充，不允许静默覆盖。

### 6.2 ProductSpec

需求产品化后的唯一产品事实来源。每次批准产生不可变版本，包含目标、用户、范围、功能、非功能要求、模块、接口、数据、风险和验收标准。

### 6.3 ProjectContract

项目级机器可读合同，定义技术栈、目录边界、模块依赖、命令、制品、部署和验收方式。推荐落盘为：

```text
.taskhub/project.yaml
.taskhub/architecture.yaml
.taskhub/acceptance.yaml
```

### 6.4 ExecutionPlan

由特定 ProductSpec 版本编译产生的执行计划，包含任务 DAG、里程碑、策略和计划版本。

### 6.5 WorkPackage

可被一个工作节点独立执行和验证的最小工作单元，包含明确输入、输出、依赖、允许修改范围、所需能力和验收命令。

### 6.6 ExecutionBatch

调度器在某一时刻根据 DAG 和运行资源计算出的可并行任务集合。批次是可重算的运行视图，不是永久业务输入。

### 6.7 TaskAttempt

一次具体任务执行。重试、故障转移和修订必须产生新的 attempt，并保留旧 attempt 的完整证据。

### 6.8 ChangeRequest

需求变化、验证失败、集成冲突或人工决定产生的受控计划变更。它说明变更原因、影响范围、废弃任务、新增任务和回归范围。

### 6.9 CapabilityPack

向产品化和执行流程提供专业规则、模板、资产和验证器的版本化能力包。前端设计包是第一类落地实现。

## 7. 产品原则

1. **规格先于实现**：开发节点只消费已批准规格和工作包。
2. **合同先于并行**：接口、数据和修改边界未冻结的任务不得盲目并行。
3. **证据先于完成**：模型声明“已完成”不能替代命令、制品和 Git 证据。
4. **历史不可覆盖**：规格、计划、尝试和能力包版本只能追加或废弃。
5. **调度与开发分离**：节点不能自行增加全局任务或改变产品目标。
6. **失败局部化**：只重新执行受影响子图，并对影响范围做可解释计算。
7. **能力可组合**：专业规则通过受信能力包组合，不写死到平台核心。
8. **平台不含业务耦合**：受管项目名称、路径和业务命令不得进入 TaskHub 核心源码。

## 8. 端到端业务流程

### 8.1 新需求流程

1. 用户选择项目并提交需求、附件和期望交付目标；
2. Intake 保存原始输入，识别缺失信息和风险；
3. Productization 生成 ProductSpec 草稿；
4. 系统推荐项目结构档案和能力包组合；
5. 项目负责人确认或修改需要人工决策的内容；
6. 批准后冻结 ProductSpec 版本及能力包锁文件；
7. Planner 生成任务 DAG 和里程碑；
8. Plan Validator 检查无环、依赖完整、任务可验收、合同兼容；
9. Scheduler 计算 Ready 任务并分配节点；
10. 节点执行工作包并返回 ChangeBundle 与证据；
11. TaskHub 验证、提交、集成并更新 DAG；
12. 失败时通过 ChangeRequest 生成修订任务；
13. 全部交付门禁通过后进入人工发布治理；
14. 发布后固化规格、计划、Git、测试、制品和审计记录。

### 8.2 需求变更流程

```text
ProductSpec v1
  -> ChangeRequest CR-001
  -> 影响分析
  -> ProductSpec v2
  -> ExecutionPlan v2
  -> 保留未受影响成果
  -> 取消或替代失效任务
  -> 执行增量任务和必要回归
```

已完成任务不得直接改写为未完成。系统通过替代任务和新的计划版本表达变化。

### 8.3 自动修订来源

自动生成 ChangeRequest 仅允许来自：

- 产品规格更新；
- 实现或验收失败；
- 架构门禁失败；
- API 或数据迁移兼容性失败；
- 安全扫描失败；
- 集成冲突；
- 上游任务输出摘要变化；
- 节点能力长期不满足；
- 人工提出的明确变更请求。

每次修订必须记录来源事件、理由、影响任务、回归范围和计划差异。

## 9. 功能需求

### FR-01 需求接入与产品化

系统必须：

- 永久保存需求原文、附件摘要、提交者和时间；
- 将需求结构化为目标、用户角色、场景、范围、排除项和验收标准；
- 识别功能需求、非功能需求、数据、API、安全、部署和迁移影响；
- 区分可合理默认的信息和必须由用户决策的信息；
- 对关键缺失信息发起一次结构化人工待办，而不是在各开发任务中重复询问；
- 输出 ProductSpec 草稿和可阅读的产品化摘要；
- 在批准前不启动项目实现任务。

ProductSpec 最低字段：

```yaml
spec_id: ps_xxx
version: 1
project_id: project_xxx
status: draft
source_requirement_ids: [req_xxx]
goals: []
personas: []
in_scope: []
out_of_scope: []
functional_requirements: []
non_functional_requirements: []
modules: []
interfaces: []
data_entities: []
security_requirements: []
delivery_requirements: []
acceptance_criteria: []
risks: []
assumptions: []
capability_pack_lock: []
```

### FR-02 产品规格版本管理

- 状态至少包括 `draft`、`in_review`、`approved`、`superseded`；
- approved 版本不可修改；
- 新版本必须引用上一版本及 ChangeRequest；
- 系统必须生成字段级差异和影响摘要；
- 运行必须明确绑定一个 ProductSpec 版本；
- 同一项目可以保留多个历史规格，但只能有一个当前生效版本；
- 未获授权角色不得批准或废弃规格。

### FR-03 项目结构档案与 ProjectContract

系统首期提供以下官方项目档案：

- `fullstack-web`；
- `backend-api`；
- `frontend-spa`；
- `python-service`；
- `worker-service`。

每个档案至少定义：

- 推荐目录结构和模块边界；
- 允许的依赖方向；
- 安装、格式化、lint、类型检查和测试命令；
- 架构、集成、构建、验收和安全命令；
- Dockerfile、Compose、健康检查和制品约定；
- README、架构文档、ADR 和环境变量示例；
- 禁止提交的凭据、缓存、依赖和构建输出。

新项目由档案生成初始 ProjectContract。接入已有项目时，系统先扫描并提出合同草稿，由项目负责人批准后生效。

### FR-04 架构合同与可执行门禁

系统必须支持声明和执行：

- 模块允许及禁止的依赖方向；
- 循环依赖检查；
- 文件、类或模块复杂度限制；
- 跨层导入和跨模块数据访问限制；
- API 合同和客户端生成一致性；
- 数据库迁移顺序、可回滚性和兼容窗口；
- 禁止凭据、生成文件和非许可二进制进入仓库；
- 项目特定的架构测试命令。

Markdown 规则必须尽量映射到一个机器检查、测试命令或人工证据。无法自动验证的规则必须明确标记为人工评审项。

### FR-05 DAG 计划生成与验证

Planner 必须为每个任务生成：

```yaml
task_id: T-001
title: 实现用户认证 API
objective: 可独立验证的任务目标
depends_on: [T-000]
inputs: []
outputs: []
allowed_paths: []
forbidden_paths: []
required_capabilities: []
contracts: []
acceptance_commands: []
expected_artifacts: []
estimated_size: small
risk_level: medium
```

计划验证必须阻止：

- 环形依赖；
- 不存在的依赖；
- 没有验收标准的实现任务；
- 输出无人消费或输入没有来源；
- 修改范围明显重叠却被声明为安全并行；
- 所需能力没有任何可用节点且不存在安装策略；
- 违反已批准 ProjectContract 的任务；
- 一个过大且无法独立验证的“完成全部功能”任务。

### FR-06 动态批次和并行调度

任务成为 Ready 必须同时满足：

```text
所有强依赖已完成
+ 输入合同已冻结
+ 修改/资源范围不与运行任务冲突
+ 存在满足能力要求的健康节点
+ 项目及平台并发预算允许
+ 没有待处理的人工治理决策
```

调度器必须：

- 根据拓扑关系动态计算并行批次；
- 支持项目级、节点级和全局并发上限；
- 结合节点角色、工具能力、CPU、内存、槽位和优先级分配；
- 支持文件路径锁、数据库迁移锁、接口冻结锁和自定义资源锁；
- 保持任务粘性，健康节点未失效时不无故迁移；
- 节点失效后创建新的 TaskAttempt 并受控故障转移；
- 使用公平调度避免一个大项目长期占满全部资源；
- 将批次、等待原因和节点选择理由持久化并展示。

### FR-07 工作包执行

每个工作节点只接收完成当前任务所需的最小上下文：

- 已批准 ProductSpec 摘要及关联条目；
- ProjectContract 及相关能力包内容；
- 上游合同和制品摘要；
- 允许与禁止修改的路径；
- 验收命令和期望制品；
- 当前任务分支、工作区和 attempt 标识；
- 不含平台密钥、其他项目凭据和无关项目数据的运行环境。

节点返回的 ChangeBundle 至少包含：

- 文件变更及基础提交；
- 实际修改范围；
- 执行命令和退出状态；
- 测试报告与制品清单；
- 合同符合性结果；
- 未解决问题和风险；
- 模型、节点、耗时和资源用量元数据。

### FR-08 集成、冲突和修订闭环

- TaskHub 控制器继续拥有权威 Git 工作区、提交、变基、合并和发布；
- 并行任务不得直接互相合并或推送权威分支；
- 每个完成任务先进行任务级验证，再进入计划级集成；
- 集成前必须确认上游提交、合同版本和工作区摘要未过期；
- 文本冲突、语义冲突、测试失败和合同失败必须分类处理；
- 可自动修复的问题生成限定范围的 revision task；
- 规格矛盾或高风险架构变化进入人工待办；
- 修订必须有最大自动次数和升级策略，不得无限循环；
- 未受影响的成功任务和证据必须复用。

### FR-09 能力包管理

能力包类型首期包括：

- `frontend-style`：视觉语言和设计令牌；
- `frontend-components`：组件体系及使用规范；
- `frontend-layout`：产品布局与页面模板；
- `brand`：Logo、品牌色、字体和图片规范；
- `project-architecture`：目录、依赖和架构门禁；
- `testing`：测试策略、命令和覆盖要求；
- `security`：安全基线和扫描规则；
- `delivery`：容器、部署、健康和制品规范。

能力包必须具有：

- 唯一 ID、语义化版本、来源和内容摘要；
- 兼容的 TaskHub 规格版本、项目档案、语言和框架；
- 明确声明的文件、模板、资产、规则和验证器；
- 许可证和资产授权信息；
- 是否包含可执行内容及所需权限；
- 安装检查、启用、停用和升级审计；
- 项目级锁定版本，不允许浮动使用 `latest`。

首期只支持平台内置和管理员导入的受信能力包，不建设公开市场。

### FR-10 前端设计包

前端设计能力由四类包组合：

1. 风格包：企业商务、现代 SaaS、极简、科技、政务、电商、数据大屏等；
2. 组件包：原生组件、Element Plus、Ant Design、Material UI、shadcn/ui 等；
3. 布局包：后台管理、门户、移动优先、数据驾驶舱、商城、内容社区等；
4. 品牌包：用户 Logo、品牌色、字体、图标、图像和禁用规则。

前端包目录合同：

```text
frontend-pack/
├── manifest.yaml
├── design-tokens.json
├── components.md
├── layouts.md
├── responsive.md
├── accessibility.md
├── assets/
├── templates/
├── skill.md
├── rules/
└── visual-tests/
```

系统必须：

- 根据 ProductSpec 和项目档案推荐最多三个兼容方案；
- 提供登录页、列表页、详情页和移动端等代表性预览；
- 允许用户选择推荐方案，或由项目默认策略自动选择；
- 生成并锁定项目 `FrontendProfile`；
- 将设计包编译为项目专属设计合同，而不是让每个节点重复解释通用包；
- 将设计令牌、组件规则、布局、响应式和无障碍要求注入相关任务；
- 通过代码规则、响应式截图、无障碍和视觉回归证据验收；
- 升级设计包时先生成影响分析和迁移任务，不直接改变已交付项目。

示例：

```yaml
frontend_profile:
  framework: vue3
  component_pack: element-plus@2.11.0
  layout_pack: admin-console@1.2.0
  style_pack: modern-enterprise@2.1.0
  brand_pack: customer-a@1.0.0
  density: compact
  theme_modes: [light, dark]
  viewports: [1440x900, 768x1024, 390x844]
```

### FR-11 证据与完成判定

任务完成不能只依赖模型文字。证据至少分为：

- `implementation`：变更摘要、文件清单和代码提交；
- `unit_test`：单元测试命令和结果；
- `integration_test`：跨模块和服务验证；
- `architecture_compliance`：依赖和结构门禁；
- `api_compatibility`：接口合同和生成物一致性；
- `migration_validation`：数据迁移与回滚验证；
- `security_scan`：凭据、依赖和静态安全扫描；
- `visual_acceptance`：截图、响应式、无障碍和视觉回归；
- `artifact_manifest`：制品名称、摘要、来源提交和构建节点；
- `git`：分支、提交、变基、合并和发布证据；
- `model_execution`：模型角色、路由、attempt 和必要的用量元数据。

Review 和 Risk 节点必须基于结构化证据判定，不得把缺失证据解释为通过。

### FR-12 暂停、恢复和幂等

- Run ID 继续作为 LangGraph thread ID；
- ProductSpec、ExecutionPlan、Task 和 Attempt 状态必须进入持久化存储；
- 控制器重启后自动恢复所有非人工等待且存在下一节点的运行；
- 相同 job ID、工作区摘要和请求内容不得重复产生副作用；
- 人工决定只通过受控 resume 命令进入图；
- interrupt 前的副作用必须幂等或在 interrupt 后执行；
- 执行结果已经成功持久化时，重放不得再次运行命令；
- 运行终止必须区分取消、失败、阻塞和被新计划替代。

### FR-13 运行可观测性

开发流程页面必须展示：

- 当前 ProductSpec 和 ExecutionPlan 版本；
- 总任务数及 Pending、Ready、Running、Verifying、Completed、Blocked 数量；
- 当前动态批次和并行任务；
- DAG 中每个任务的状态、依赖和阻塞原因；
- 节点分配、槽位和预计等待原因；
- ChangeRequest、计划差异和受影响子图；
- 里程碑进度和关键路径；
- 测试、架构、视觉、制品和 Git 证据摘要。

批次不重新成为用户手工输入。用户控制的是项目并发策略和资源预算，而不是手工维护批次编号。

### FR-14 人工治理

以下事项默认需要项目负责人或管理员确认：

- 首个 ProductSpec 批准；
- 会改变产品范围或关键验收标准的规格更新；
- 不兼容 API、破坏性数据库迁移或高风险架构调整；
- 安全基线例外；
- 能力包来源不受信或包含高权限可执行内容；
- 发布到受保护环境。

低风险实现修订、测试修复和无接口变化的局部冲突可以按项目策略自动继续。

### FR-15 项目生产画布

TaskHub 必须提供一个可视化项目生产画布，使操作者能够在同一空间内创建项目和生产资源卡片、连接有效关系，并观察需求从产品化到开发、测试、集成和发布候选的自动流转。

画布必须严格区分两个语义层：

1. **生产拓扑层**：由用户配置，表达项目可以使用哪些控制、执行、测试和预生产资源；
2. **交付运行层**：由 TaskHub 根据 ProductSpec 和 ExecutionPlan 自动生成，表达任务 DAG、动态批次、实时状态和证据流。

用户连线定义资源路由和调度资格，不直接修改任务依赖。任务依赖只能由计划控制器根据已批准规格生成，或通过受控 ChangeRequest 修订。

#### 15.1 画布节点类型

首期支持以下节点卡片：

| 节点类型 | 作用 | 创建方式 |
| --- | --- | --- |
| 项目节点 | 录入需求、显示规格、计划、进度和交付状态 | 用户创建或绑定已有项目 |
| 控制节点 | 表达负责产品化、规划、调度、集成和治理的 Seed 控制面 | 绑定当前控制器，管理员配置 |
| 执行节点 | 承担编码、构建或通用执行工作负载 | 绑定已有工作节点或发起受控创建 |
| 测试节点 | 承担单元、集成、架构、安全和视觉测试 | 绑定已有工作节点或发起受控创建 |
| 预生产节点 | 承担候选部署、健康检查和浏览器验收 | 绑定已有工作节点及项目预生产配置 |
| 资源池节点 | 将多个同角色节点组织为一个调度目标 | 管理员或项目负责人创建 |

在画布中“创建节点卡片”不等于立即创建物理设备或容器。项目节点可以创建或接入项目；执行、测试和预生产节点可以绑定现有资源，也可以在明确确认后调用既有持久化节点创建流程。首期控制节点是绑定当前 Seed 的逻辑编排节点，不伪装为已经创建了多个物理控制器。未来支持多控制器时再扩展其准入和高可用合同。

项目卡片必须允许输入开发需求。提交后自动执行：

```text
需求输入
  -> 产品化控制器
  -> ProductSpec 草稿/批准
  -> ExecutionPlan 与任务 DAG
  -> 动态开发批次
  -> 执行节点
  -> 测试节点
  -> 集成与修订
  -> 预生产验收
  -> 发布治理
```

自动生成的步骤、批次和任务不得要求用户逐个手工连线。系统必须根据 DAG 和已激活生产拓扑自动路由。

#### 15.2 连线类型

所有连线必须是有方向、有类型、可校验的业务关系，不允许保存无语义的装饰线。

| 连线类型 | 示例 | 业务含义 |
| --- | --- | --- |
| `governed_by` | 项目 -> 控制节点 | 该控制面负责项目规格、计划和治理 |
| `executes_on` | 控制节点/项目 -> 执行节点或资源池 | 开发任务可调度到目标资源 |
| `verified_by` | 项目/执行池 -> 测试节点或资源池 | 指定验证资源和能力范围 |
| `accepted_by` | 项目 -> 预生产节点 | 指定候选部署和验收资源 |
| `fallback_to` | 资源池/节点 -> 资源池/节点 | 主资源不可用时的受控后备路径 |

连接建立时必须立即检查：

- 起点和终点类型是否合法；
- 是否形成不允许的控制环；
- 项目是否存在唯一有效控制路径；
- 执行、测试和预生产节点是否具备声明能力；
- 当前操作者是否有权绑定该项目和资源；
- 资源是否处于可调度状态；
- 跨主机、网络和凭据前置条件是否满足；
- 新连接是否影响正在运行的任务。

错误连线不得进入激活拓扑，界面必须说明原因和修复建议。

#### 15.3 草稿、验证与激活

画布编辑使用版本化拓扑，不允许拖拽或连线后立即改变生产调度：

```text
Topology Draft
  -> Validate
  -> Activate
  -> Supersede by New Version
```

- 节点位置、分组和缩放属于用户布局；
- 节点绑定、边类型、路由、资源池和策略属于生产拓扑；
- 激活前必须服务端验证；
- 激活产生不可变拓扑版本和审计记录；
- 新拓扑默认只影响尚未分配的任务；
- 是否迁移 Running 任务必须通过明确治理操作，默认不迁移；
- 删除已绑定资源必须先排空或提供替代路径；
- 控制器重启后恢复相同激活版本和画布布局。

#### 15.4 运行态叠加

画布运行态必须在生产拓扑上叠加展示：

- 项目总体状态、ProductSpec 和 ExecutionPlan 版本；
- 当前动态批次及每批任务数量；
- Pending、Ready、Running、Verifying、Completed、Blocked 数量；
- 任务实际流向的控制、执行和测试节点；
- 节点槽位、负载、健康和等待原因；
- 失败、故障转移、修订和回滚路径；
- 关键证据摘要和最后更新时间。

运行时动画只用于帮助理解短暂状态变化，并尊重 `prefers-reduced-motion`。状态必须同时使用文字、形状或线型表达，不能只依赖颜色和动画。

#### 15.5 画布交互

桌面端必须支持：

- 空白处右键创建允许的节点；
- 节点右键执行配置、复制、停用、删除等有权限操作；
- 从明确的连接端口拖线，并在悬停时显示合法目标；
- 框选、多选、拖拽、缩放、平移、自动布局、适应视图和小地图；
- 撤销、重做，以及离开未保存草稿前的提醒；
- 单击节点打开摘要，双击或明确操作打开详情侧栏；
- 从画布直接进入任务、规格、节点诊断和证据详情。

右键不是唯一操作入口。必须提供“添加节点”工具栏、键盘可访问的上下文菜单和节点/连线列表视图。触摸设备通过长按或明确按钮进入同一操作，不能依赖鼠标悬停。

窄屏首期以查看、筛选、状态和详情为主，复杂布线可引导到桌面端；同时保留等价的拓扑列表编辑能力，不能因无法拖线而阻断核心配置。

#### 15.6 技术演进边界

项目画布同时满足“复杂共享可编辑状态”和“缩放、拖拽、大型拓扑可视化”两个 React 迁移条件。画布正式实施前应建立独立 `taskhub-web`：

- React + TypeScript + Vite；
- React Flow 或经技术验证的等价画布引擎；
- TanStack Query 管理服务端状态；
- TaskHub 自有设计令牌和业务节点组件；
- 现有 FastAPI API/SSE 继续作为稳定后端边界。

迁移必须按页面或路由渐进进行，现有任务中心、开发流程和系统配置在等价能力验证前继续可用。不得为画布局部需求在现有原生 JavaScript 中堆叠不可维护的简化图编辑器。

## 10. 状态模型

### 10.1 ProductSpec

```text
draft -> in_review -> approved -> superseded
  |          |
  +----------+-> rejected
```

### 10.2 ExecutionPlan

```text
draft -> validating -> active -> completed
             |          |
             v          +-> superseded
          invalid
```

### 10.3 Task

```text
pending -> ready -> assigned -> running -> verifying -> completed
   |         |         |          |           |
   +---------+---------+----------+-----------+-> blocked
                                                -> revision_ready
                                                -> cancelled
                                                -> superseded
```

### 10.4 TaskAttempt

```text
created -> dispatched -> running -> result_received -> validated
                |           |             |
                +-----------+-------------+-> failed
                                             -> timed_out
                                             -> abandoned
```

Task 与 TaskAttempt 必须分离：任务表达业务目标，attempt 表达一次具体执行。

### 10.5 ProductionTopology

```text
draft -> validating -> active -> superseded
            |
            +-> invalid
```

同一画布可以保存多个草稿，但每个调度作用域只能有一个激活拓扑版本。拓扑激活和计划激活彼此独立：前者规定任务允许流向哪里，后者规定任务必须以什么依赖顺序执行。

## 11. 数据关系

```text
Project
├── ProductionTopology Version
│   ├── Canvas Node
│   ├── Typed Edge
│   ├── Resource Pool
│   └── Layout
├── Requirement
├── ProductSpec Version
│   ├── ProjectContract Version
│   ├── CapabilityPack Lock
│   └── ExecutionPlan Version
│       ├── Task DAG
│       │   └── TaskAttempt
│       ├── ExecutionBatch Snapshot
│       ├── ChangeRequest
│       └── Milestone
├── Evidence
├── Artifact
└── Publication
```

所有核心对象至少包含：稳定 ID、项目 ID、版本或 revision、创建者、创建时间、状态、来源对象和内容摘要。

## 12. 控制器职责边界

### 12.1 产品化控制器

负责需求澄清、ProductSpec、能力包推荐、变更影响分析和产品级人工决策。

### 12.2 计划控制器

负责将规格编译为 DAG，验证依赖、任务大小、合同、输入输出和可验收性。

### 12.3 调度控制器

负责 Ready 计算、并发预算、资源锁、节点选择、attempt、超时和故障转移。

### 12.4 集成控制器

负责 ChangeBundle 验证、Git 集成、架构/API/迁移检查、回归范围和发布候选。

### 12.5 执行节点

只负责完成工作包、运行授权命令和返回证据。执行节点不得批准规格、修改全局 DAG、直接发布权威分支或读取平台根凭据。

## 13. 前端产品需求

### 13.1 信息架构

保持当前三个一级入口，不在本阶段增加第四个一级菜单：

```text
任务中心
开发流程
  ├── 项目生产画布
  ├── 当前项目与仓库
  ├── 产品规格
  ├── 设计与能力包
  ├── 执行计划与 DAG
  ├── 当前运行与人工待办
  └── 交付证据
系统配置
  ├── 运行概览
  ├── 模型服务
  ├── 物理主机
  ├── 工作节点
  └── 平台设置 / 能力包管理
```

项目能力包选择属于开发流程的项目上下文；能力包来源、安装、信任和全局库存属于系统配置。

### 13.2 产品规格界面

- 展示原始需求与结构化规格的对应关系；
- 先展示目标、范围、待决策事项和验收摘要；
- 支持版本切换和字段级差异；
- 清楚区分草稿、待评审、已批准和已废弃；
- 批准按钮仅对授权角色显示；
- 长规格按主题渐进披露，不在一个大文本框中编辑全部内容。

### 13.3 DAG 与批次界面

- 默认提供可读的分层任务列表和动态批次视图；
- 展示依赖、状态、节点、锁和阻塞原因；
- 当任务量或交互复杂度达到现有设计规范的 React 迁移阈值时，再引入可缩放 DAG 画布；
- 视觉图不是状态来源，所有任务关系必须来自服务端；
- 无法使用图形界面时，键盘和文本视图仍能完成核心操作。

### 13.4 能力包选择界面

- 系统推荐不超过三个兼容组合；
- 每个组合展示名称、用途、预览、版本、兼容性和验证能力；
- 前端方案至少展示桌面和手机代表性预览；
- 默认选项明确，允许查看高级组合配置；
- 不兼容组合必须阻止保存并说明原因；
- 项目锁定版本、可用升级和升级影响清晰可见。

### 13.5 现有设计边界

TaskHub 控制台继续遵守 `docs/frontend-design.md`：可信、克制、清晰、高密度。能力包用于受管项目的前端成果，不改变 TaskHub 控制台自身的视觉身份。

在实际实现新的产品规格、DAG 或能力包界面时，必须同步修订 `docs/frontend-design.md`，并保持认证、SSE、现有 DOM/API、响应式和无障碍能力不回归。

## 14. API 与事件要求

具体路径可在技术设计阶段确定，但 API 必须覆盖以下资源：

- requirements；
- product-specs 及版本差异；
- project-contracts；
- execution-plans；
- tasks、dependencies 和 attempts；
- change-requests；
- capability-packs、compatibility 和 project locks；
- evidence 和 artifacts；
- scheduling decisions 和 resource locks。
- production-topologies、canvas-nodes、typed-edges 和 resource-pools；

写入 API 必须具备：

- 登录、CSRF 和 RBAC；
- 乐观并发版本，拒绝静默覆盖；
- 请求幂等键；
- 输入 Schema 校验；
- 审计事件；
- 不返回凭据、模型令牌和节点密钥。

SSE 或后续等价事件通道至少发布：

- 规格状态变化；
- 计划激活或被替代；
- 任务和 attempt 状态变化；
- 批次重新计算；
- 生产拓扑草稿验证、激活和替代；
- 节点分配和故障转移；
- ChangeRequest 和人工待办；
- 验证、集成和发布结果。

## 15. 权限要求

| 操作 | 管理员 | 项目负责人 | 开发人员 | 审计人员 |
| --- | --- | --- | --- | --- |
| 查看项目规格和计划 | 是 | 是 | 是 | 是 |
| 提交项目需求 | 是 | 是 | 是 | 否 |
| 批准 ProductSpec | 是 | 是 | 否 | 否 |
| 调整项目并发策略 | 是 | 是 | 否 | 否 |
| 处理普通修订待办 | 是 | 是 | 是 | 否 |
| 批准高风险例外和发布 | 是 | 按项目策略 | 否 | 否 |
| 安装和信任能力包 | 是 | 否 | 否 | 否 |
| 为项目选择已信任能力包 | 是 | 是 | 否 | 否 |
| 查看完整审计证据 | 是 | 是 | 按项目权限 | 是 |

服务端权限是唯一事实来源，前端隐藏操作不能替代 API 鉴权。

## 16. 非功能需求

### 16.1 可靠性

- 控制器重启后不得丢失已批准规格、活动计划、任务和 attempt；
- 重复事件和重复回调不得产生重复提交、任务或制品；
- 单节点失效不得使整个无关任务图失败；
- 数据库事务保证状态迁移与审计事件一致。

### 16.2 性能与规模首期目标

- 单项目支持至少 500 个任务节点的 DAG；
- 单一 TaskHub 部署支持至少 20 个同时 Running 的任务；
- 1,000 个任务以内的 Ready 重算目标小于 2 秒；
- 常规状态更新至前端可见目标小于 3 秒；
- 任务列表和 DAG 文本视图必须分页或虚拟化，不能一次渲染无限历史。

这些是首期工程目标，不等于承诺所有模型调用在固定时间完成。

### 16.3 安全

- 能力包默认视为不可信输入，安装前校验路径穿越、链接、设备文件和清单；
- 包内可执行内容必须显式声明、管理员确认并在受限节点运行；
- 资源和模板不得携带凭据；
- 运行上下文按项目和任务最小化；
- 日志、证据和诊断继续执行凭据脱敏；
- Git 地址不得包含密码或访问令牌。

### 16.4 可解释性

系统必须能回答：

- 为什么存在这个任务；
- 为什么它现在可以或不可以运行；
- 为什么选择这个节点；
- 为什么发生重新规划；
- 为什么本次验证判定失败或通过；
- 哪个规格和能力包版本产生了当前成果。

### 16.5 可测试性

- 核心状态转换、DAG 验证和调度规则使用确定性测试替身；
- 计划生成与执行分离，使规划输出可以独立做 Schema 和不变量测试；
- 所有能力包至少有清单、兼容性、编译和验收夹具；
- 前端新增结构必须具备桌面和窄屏回归；
- 不依赖实时模型完成基础单元测试。

## 17. 成功指标

首期上线后持续观察：

1. 产品规格首次批准后因歧义产生的返工率；
2. 平均可并行任务数和节点槽位利用率；
3. 关键路径交付时长相对线性执行的下降比例；
4. 因文件或合同冲突导致的集成失败率；
5. 失败后复用成功任务的比例；
6. 控制器重启后的自动恢复成功率；
7. 任务证据完整率；
8. 能力包项目的视觉、架构和安全门禁通过率；
9. 需要平台维护人员介入的受管项目运行比例；
10. 用户从输入需求到首个可验收版本的总时长。

## 18. 实施阶段与批次

### Phase 0：领域模型与兼容基线

目标：先稳定生产系统的事实模型，不改变现有运行结果。

- 定义 ProductSpec、ExecutionPlan、Task、TaskAttempt、ChangeRequest 和 CapabilityPack Schema；
- 建立数据库迁移、仓储接口和状态不变量；
- 将现有线性运行映射为单计划、单批次兼容视图；
- 保留现有 `default` 生产线兼容值；
- 建立功能开关和迁移回滚策略。

验收：现有测试和历史运行读取不回归；新对象可以创建、持久化和重载；非法状态转换被拒绝。

### Phase 1：需求产品化与版本规格

目标：用户输入先形成稳定的产品规格。

- 实现结构化 Intake 和 Productization；
- 实现 ProductSpec 草稿、评审、批准、差异和废弃；
- 实现产品级人工待办；
- 开发流程页面展示规格摘要和版本。

验收：未经批准的规格不能启动实现；批准版本不可修改；变更产生新版本和可读差异。

### Phase 2：ProjectContract 与结构门禁

目标：形成可执行的一体化项目结构。

- 实现 `.taskhub/*.yaml` Schema；
- 提供首批官方项目档案；
- 新建项目生成合同，已有项目生成待确认合同草稿；
- 将架构、API、迁移、安全和制品检查纳入证据。

验收：故意制造的跨层依赖、循环依赖、错误迁移和缺失制品能够被门禁阻止。

### Phase 3：DAG 计划与持久化调度

目标：由系统自动形成批次并并行执行无依赖任务。

- 实现 DAG 生成、Schema 和不变量验证；
- 实现 Ready 计算、资源锁、并发预算和公平调度；
- 实现 TaskAttempt、节点故障转移和重启恢复；
- 在开发流程展示任务依赖、批次和等待原因。

验收：至少两个无依赖任务在两个节点并行运行；依赖任务等待；冲突任务串行；重启后不重复执行成功命令。

### Phase 3A：项目生产画布与拓扑路由

实施状态：已完成。独立 `taskhub-web`、版本化拓扑、服务端校验/激活、调度资格约束、
资源池、运行态叠加和等价列表入口已交付；后续功能从 Phase 4 继续。

目标：通过可视化画布配置项目与生产资源关系，并观察自动交付流转。

- 建立独立 `taskhub-web` 前端基础和渐进迁移边界；
- 实现项目、控制、执行、测试、预生产和资源池节点卡片；
- 实现右键菜单、工具栏、键盘入口、拖线和拓扑列表等价操作；
- 实现有类型连线、服务端拓扑验证、版本和激活；
- 将激活拓扑接入调度资格和资源池选择；
- 将自动生成的 ProductSpec、DAG、动态批次和运行状态叠加到画布；
- 保留现有开发流程作为兼容视图，直至能力等价。

验收：用户能从空画布创建或绑定一个项目、一个控制节点、两个执行节点和一个测试节点，形成合法拓扑；项目输入需求并批准规格后，无依赖任务自动并行流向两个执行节点，再进入测试节点；非法连线无法激活；控制器重启后拓扑、布局和运行状态恢复；全部核心操作存在非右键入口。

### Phase 4：集成与持续修订

实施状态：已完成。ChangeRequest 影响分析、版本化增量计划、任务替代、历史 attempt
保留、验证证据复用、局部回归范围和自动修订上限均已交付；后续功能从 Phase 5 继续。

目标：失败和需求变化进入受控增量闭环。

- 实现 ChangeRequest 和影响分析；
- 实现计划版本、任务替代和受影响子图；
- 实现自动修订上限和人工升级；
- 实现并行变更的集成、回归范围和证据复用。

验收：修改一个局部需求只重跑受影响任务；失败修订不覆盖原 attempt；无限修订被策略阻止。

### Phase 5：能力包框架与前端设计包

实施状态：已完成。受信库存、兼容解析、项目精确版本锁、三方案预览、
ProjectDesignContract 编译、任务上下文注入、验证证据声明和显式升级迁移均已交付；
后续功能从 Phase 6 继续。

目标：允许项目选择受信、可版本化和可验证的专业能力。

- 实现能力包清单、库存、信任、兼容和锁文件；
- 实现前端风格、组件、布局和品牌包；
- 实现三方案推荐和代表性预览；
- 编译 Project Design Contract；
- 接入响应式、无障碍和视觉回归证据。

验收：同一项目所有前端任务使用锁定版本；不兼容组合无法启用；设计包升级产生迁移计划而不是静默变化。

### Phase 6：规模化、策略和产品完善

目标：达到多项目、多生产线持续运行能力。

- 优化大 DAG 计算、分页和可观测性；
- 完善配额、优先级、公平性和成本策略；
- 增加执行预测、关键路径和瓶颈分析；
- 完成正式权限、审计、备份恢复和升级验证；
- 评估并渐进迁移 `taskhub-web` 的其余控制台页面，避免双前端长期重复维护。

验收：达到第 16 节规模目标；多项目并发不饥饿；完整发布和恢复演练通过。

实施状态：源代码能力已完成。项目策略冻结、20 并发预算、加权公平、成本门禁、千任务
Ready 聚合、关键路径/瓶颈分析、服务端分页、生产就绪检查和前端迁移边界均已交付。权限、
审计、备份恢复与升级合同纳入自动化验证；按本阶段发布约束，真实目标环境发布/恢复演练
保留为正式部署时的运维门禁，不伪记为本次源代码阶段已执行。详见
`docs/requirements/productized-delivery-phase-6.md`。

## 19. 总体验收场景

以下端到端场景全部通过，才能认定本 PRD 核心完成：

1. 用户输入一个包含前后端、数据库和部署的软件需求；
2. TaskHub 生成 ProductSpec 草稿、待决策项和三个兼容前端方案；
3. 用户批准规格及选定设计包；
4. 系统生成无环 DAG，明确任务输入、输出、路径和验收；
5. 两个以上无依赖任务被分配到不同健康节点并行执行；
6. 依赖任务只在上游验证通过后进入 Ready；
7. 两个修改范围冲突的任务不会同时运行；
8. 某任务失败后生成新 attempt 或 revision task，其他成功任务不重跑；
9. 控制器在任务运行中重启，恢复后不产生重复 Git 提交和重复制品；
10. 前端成果使用锁定设计令牌和组件规范，桌面、平板、手机截图及无障碍检查通过；
11. 架构、API、迁移、安全、测试、视觉和制品证据全部进入评审；
12. 发布审批后，权威仓库获得经过验证的提交，并能追溯到需求、规格、计划、任务和模型执行。
13. 用户可以在项目画布建立并激活合法生产拓扑，输入需求后观察任务批次自动流经控制、执行和测试资源。
14. 画布右键、工具栏、键盘和列表模式均可完成对应核心操作，错误连线不会改变活动调度。

## 20. 兼容与迁移要求

- 现有运行在迁移后显示为 Legacy Linear Plan，不伪造新的详细 DAG 证据；
- 现有项目命令映射到 ProjectContract 初始版本，须标记来源为 migrated；
- 现有任务中心、项目选择、仓库、预生产验收、SSE 和发布流程继续工作；
- 数据迁移优先采用增量表和可空引用，不一次性破坏旧状态结构；
- 新调度器使用功能开关按项目启用，稳定后再成为默认；
- 任何迁移失败不得修改受管项目仓库或丢失现有 LangGraph checkpoint；
- 前端实现期间继续遵守当前静态资源版本和响应式验证要求。

## 21. 风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| 规划模型生成错误或过细 DAG | 强 Schema、不变量验证、任务大小策略、计划评审 |
| 并行导致语义冲突 | 接口冻结、路径/资源锁、集成验证、受影响回归 |
| 状态模型与 LangGraph checkpoint 重复 | 明确领域事实与图运行状态的所有权，使用事务和事件关联 |
| 能力包成为任意代码执行入口 | 受信来源、内容摘要、权限声明、隔离验证、管理员批准 |
| 规格频繁变化造成计划抖动 | 已批准版本不可变、变更合并窗口、计划版本和废弃规则 |
| 自动修订无限循环 | attempt/revision 上限、失败分类、人工升级 |
| 大 DAG 前端难以使用 | 文本视图优先、分组/筛选/分页，达到阈值后迁移 React 图形界面 |
| 画布连线被误解为任务依赖 | 区分生产拓扑和交付运行两层，使用有类型连线和只读运行叠加 |
| 拖拽操作直接扰动运行任务 | 草稿、服务端验证、显式激活，新拓扑默认只影响未分配任务 |
| 证据数量快速膨胀 | 摘要与原始制品分层、保留策略、内容摘要去重 |
| 能力包组合不兼容 | 兼容矩阵、解析器、锁文件和启用前预检 |

## 22. 待技术设计确认事项

以下事项不阻止 PRD 进入 Phase 0，但必须在对应阶段技术设计中确定：

1. ProductSpec 和 Task DAG 是全部存入 PostgreSQL，还是大文档进入制品存储并在数据库留索引；
2. 领域状态与 LangGraph state 的单一写入入口和事务边界；
3. 路径锁与语义资源锁的冲突判定算法；
4. DAG 重新计算采用全量还是增量拓扑更新；
5. 能力包的签名格式、导入格式和受信根管理；
6. 视觉回归采用像素、结构化规则、视觉模型或组合策略；
7. React 迁移是否与 DAG 可视化同期进行；
8. 规格批准是否允许项目策略配置为低风险自动批准；
9. 模型成本、任务优先级和资源配额的默认算法。
10. 生产拓扑与现有节点注册表、物理主机和项目权限的聚合模型；
11. 画布最大节点规模、分区加载、布局算法和协同编辑策略；

## 23. 完成定义

某一阶段只有同时满足以下条件才算完成：

- 功能代码、数据库迁移、API 和前端均符合本 PRD；
- 相关状态不变量和权限有自动化测试；
- 重启、重放和重复请求不产生重复副作用；
- 失败路径、回滚和人工恢复方式已验证；
- 架构、测试、安全、制品和 Git 证据完整；
- 文档、Schema、示例能力包和操作说明同步更新；
- 不直接修改任何受 TaskHub 管理的项目；
- 正式部署仍需单独授权，并遵守备份、健康检查和回滚要求。
