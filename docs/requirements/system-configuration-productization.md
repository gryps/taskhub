# TaskHub 系统配置产品化重构需求

状态：阶段四（首次启动与系统就绪 Alpha）开发完成

版本：0.5

更新日期：2026-09-10

## 1. 背景

TaskHub V2 当前“系统配置”同时展示系统检测、模型资源、执行节点、节点容器、节点负载、验收前置配置和预生产环境。随着产品架构收敛为 `taskhub-seed` 控制面、SSH 纳管物理主机和统一 `taskhub-node` 工作镜像，原页面出现以下问题：

- 执行节点、节点容器和节点负载描述同一个工作节点的不同状态，用户需要在多个栏目间交叉判断；
- 系统检测与验收前置配置重复展示节点能力和失败项；
- 预生产环境属于项目，而不是全局系统；
- 模型、主机和平台参数缺少可管理的产品配置入口；
- Docker 容器等实现术语占据一级信息位置，没有围绕用户管理对象组织页面。

## 2. 目标

将系统配置重构为按资源对象组织的产品管理界面：

```text
系统配置
├── 运行概览
├── 模型服务
├── 物理主机
├── 工作节点
└── 平台设置

项目设置
├── 仓库与分支
├── 构建与测试
├── 测试数据库
└── 预生产与验收环境
```

第一阶段复用现有 API 完成信息架构收敛，不以无效表单假装已经具备配置能力。后续阶段补齐安全配置存储、远程 SSH 主机管理和统一工作镜像生命周期。

## 3. 现有栏目处置

| 现有栏目 | 目标位置 | 处置 |
| --- | --- | --- |
| 系统检测 | 运行概览 | 只保留控制面、数据库、存储等全局运行条件；节点详情归入工作节点 |
| 模型资源 | 模型服务 | 保留状态和用量，后续增加 Provider、路由、角色模型和密钥配置 |
| 执行节点 | 工作节点 | 与容器状态、负载、能力合并 |
| 节点容器 | 工作节点 | 作为节点生命周期实现，不再作为一级业务资源 |
| 节点负载 | 工作节点详情 | 展示 CPU、内存、磁盘和槽位 |
| 验收前置配置 | 工作节点 / 项目设置 | 浏览器和工具归节点；测试数据库及验收目标归项目 |
| 预生产环境 | 项目设置 | 保留项目级 API 和数据模型，从系统配置移出 |

## 4. 模块需求

### 4.1 运行概览

运行概览回答“当前 TaskHub 是否具备开始交付的条件”。至少展示：

- Seed 控制面、LangGraph 检查点、数据库和持久化目录状态；
- 模型、物理主机和工作节点的汇总状态；
- 阻塞交付的失败项和可执行修复建议；
- 当前版本和最近检测时间。

运行概览不得完整复制节点负载、工具能力和容器操作。失败项应能引导用户前往相应模块处理。

### 4.2 模型服务

当前阶段保留 Provider 状态、模型路由、角色模型、账号用量和最后错误。产品化配置阶段增加：

- Provider 类型、API 地址和代理策略；
- 规划、编码、审查、风险和监督角色的模型选择；
- API Key 或账号授权引用；
- 超时、重试和冷却策略；
- 测试连接、保存、生效状态和修改审计。

密钥只允许新增或替换，API 不得返回原文。

### 4.3 物理主机

物理主机是安装 Docker 并承载 `taskhub-node` 的设备。主机登记字段包括：

- 显示名称、IP 或域名、SSH 端口和 SSH 用户；
- SSH 密钥引用和 Docker 权限方式；
- 标签、用途、镜像代理和备注。

保存前依次完成 SSH 连接、主机指纹确认、Docker 权限、硬件资源、镜像架构和 Node Agent 回连条件检测。远程主机管理的完整安全要求以 `seed-ssh-multihost.md` 为准。

在 SSH 后端交付前，页面只能明确显示 Seed 本机 Docker 能力和“远程主机待实现”状态，不显示可提交的远程主机表单。

### 4.4 工作节点

工作节点统一表达物理主机、容器和 Node Agent 三层状态。列表至少展示：

- 节点 ID、物理主机和角色；
- 期望状态、容器状态和 Agent 健康状态；
- 工作负载、槽位、CPU、内存和磁盘摘要；
- 镜像版本、最后心跳和最近错误；
- 启动、停止、重启、升级、日志和移除操作。

创建节点的目标表单包括目标主机、节点 ID、显示名称、角色、槽位、CPU/内存/磁盘限制、镜像版本、数据卷和重启策略。当前本机 Alpha 可以继续只要求节点 ID、角色和槽位，但必须标明创建目标是 Seed 本机。

浏览器、Codex、Git、Node.js、测试数据库访问等前置条件作为节点“能力与前置条件”展示，不再作为一级栏目。

### 4.5 平台设置

平台设置用于低频全局参数：

- Seed 对外地址和 Node Agent 回连地址；
- 默认工作节点镜像、镜像仓库和代理；
- 默认资源限制、心跳与离线阈值；
- 日志和制品保留策略；
- TLS、安全 Cookie、备份和配置导出状态。

数据库连接、会话密钥、配置加密主密钥等启动根配置继续由 Docker Secret 或环境变量提供，不允许普通 Web API 回读。

### 4.6 项目设置

预生产与验收环境移动到开发流程的项目上下文中。当前字段继续包括项目、测试访问地址、Edge 主机、Origin 主机和环境标识。后续扩展：

- 部署目标或预生产节点选择；
- 部署、健康检查和回滚契约；
- 项目级测试数据库引用；
- 项目凭据引用和最小授权范围。

预生产节点是执行部署与验收的计算资源；预生产环境是项目部署目标，两者不得混为一个对象。

## 5. 配置存储与安全

配置分为三层：

1. 启动根配置：数据库、会话密钥、加密主密钥，由部署环境注入；
2. 平台管理配置：模型、主机、节点、镜像策略，持久化到数据库；
3. 项目配置：仓库、测试、数据库、预生产和验收契约，随项目记录持久化。

API Key、SSH 私钥和节点令牌必须加密存储。前端只显示是否已配置和脱敏摘要。配置修改必须记录操作者、对象、参数摘要、时间、测试结果和生效状态。需要重启的修改必须明确提示。

## 6. 交互要求

- 一级资源模块使用一致的折叠标题、摘要和刷新操作；
- 工作节点内部使用小标题区分“节点状态、创建节点、容器生命周期、资源负载、能力与前置条件”；
- 破坏性操作不得使用主按钮样式；
- 状态同时使用文字和颜色；
- 错误包含原因和修复建议；
- 窄屏横向滚动限制在资源表格内部；
- 尚未实现的能力必须标记为待交付，不提供会丢失输入的假保存按钮。

## 7. 实施阶段

### 阶段一：信息架构快速重构

- 收敛为运行概览、模型服务、物理主机、工作节点、平台设置；
- 合并执行节点、容器、负载和节点前置条件；
- 将预生产环境移动到项目设置；
- 保留现有 API、认证、CSRF 和节点生命周期能力。

### 阶段二：可管理配置

- 建立数据库配置模型和加密敏感值存储；
- 实现模型服务和平台设置写入 API；
- 增加连接测试、生效状态和操作审计。

当前快速开发实现使用 `taskhub_managed_config` 保存期望配置，使用
`taskhub_config_audit` 保存配置操作。API Key 由部署注入的
`TASKHUB_CONFIG_ENCRYPTION_KEY` 进行 Fernet 加密；读取 API 只返回是否已配置、
脱敏摘要和来源。配置保存后进入“等待重启”状态，下一次 Seed 启动装载成功后
才标记为“已生效”。

### 阶段三：多主机节点编排

- 实现物理主机库存、SSH 指纹和准入检测；
- 创建节点时选择目标主机和资源规格；
- 实现远程生命周期、期望状态协调、升级与回滚；
- 使用完整统一的 `taskhub-node` 镜像。

阶段三 A 已实现物理主机库存、SSH 指纹确认、加密私钥、SSH/Docker/硬件资源/
Node Agent 回连准入检测和重新检测。主机只有在操作者确认指纹且强制检测全部通过
后才进入可用状态。

阶段三 B 第一版将自由文本“用途”替换为系统固定的可承载角色集合，并实现选择已
准入主机、远程拉取统一 `taskhub-node` 镜像、创建容器、Agent 健康确认、调度注册、
启动、停止、重启和移除。远程节点关系持久化到数据库；镜像摘要、主机、角色、端口、
资源限额和期望/实际状态均保留。逐节点加密凭据及创建、轮换、删除吊销链路已经实现；
后台协调器定期比较数据库期望状态、远程容器和 Agent 健康状态，并在失联时停止调度、
恢复时重新纳管。镜像版本升级与失败回滚仍是后续增量。

阶段三 B 第二版将远程创建改为后台分阶段操作。Seed 依次尝试私有仓库、国内镜像
代理前缀和镜像原始地址；远程拉取均失败时，从 Seed 本机 Docker Engine 导出同名
镜像，通过严格主机指纹 SSH 流传输到目标主机并执行 `docker load`。私有仓库密码
沿用配置加密根密钥加密保存，只允许替换、不回显；远端登录使用临时
`DOCKER_CONFIG`，操作结束即删除。取得镜像后必须核对 Linux 操作系统、CPU 架构和
镜像摘要，再创建容器。工作节点列表轮询展示拉取、传输、校验、创建和健康检查进度，
错误保存在节点记录中供刷新后诊断。

### 阶段四：首次启动与系统就绪

- 首次登录后自动展示 Seed 初始化状态；
- 读取 Docker Engine CPU、内存、架构及 TaskHub 持久化磁盘；
- 复用现有配置栏目引导完成地址、镜像、模型、主机和节点配置；
- 支持从 Web 导入 `docker save` 离线镜像包；
- 模型或平台配置等待生效时支持 Web 快速重启 Seed 容器；
- 统一判断并显示“系统已具备运行任务条件”。

详细契约见 `seed-first-run-onboarding.md`。

## 8. 阶段一验收标准

1. 系统配置只显示五个全局资源模块。
2. 执行节点、容器、负载和验收能力在同一个工作节点模块中呈现。
3. 预生产环境配置只在开发流程的项目设置中出现。
4. 本机容器创建、启动、停止和移除功能不回归。
5. 系统检测、模型状态、节点状态、节点负载和项目环境检测功能不回归。
6. 物理主机和平台设置如实展示当前能力边界，不接受无法持久化的输入。
7. 1440px 与 680px 布局无页面级横向溢出，表格溢出保留在自身容器内。
8. 前端静态资源版本、语法检查和相关自动化测试通过。

## 9. 阶段二验收标准

1. 模型服务和平台设置均可从 Web 读取与保存，并受登录和 CSRF 保护。
2. API Key 只允许新增或替换，数据库只保存密文，任何读取和审计响应均不含原文。
3. 数据库、会话密钥、配置加密主密钥和节点令牌不进入 Web 可管理字段。
4. 模型服务支持服务端连接测试，结果写入审计且错误信息不暴露凭据。
5. 保存后的期望配置与当前生效配置分别展示；需要重启时必须明确提示。
6. Seed 启动成功装载新配置后，配置版本才标记为已生效。
7. 平台参数校验心跳与离线阈值、镜像引用、URL 和资源默认值。
8. Seed 安装脚本能够生成配置加密主密钥，现有 `.env` 能安全补齐该字段。

## 10. 阶段三 A 验收标准

1. 物理主机页面提供主机 ID、名称、地址、SSH 端口、用户、Docker 权限、固定可承载角色、标签、私钥和备注字段。
2. 首次检测只返回 SSH 主机指纹；用户明确确认后才执行认证和准入。
3. 私钥由配置根密钥加密保存在 PostgreSQL，列表、审计和 API 响应不返回密文或明文。
4. 主机准入检测 SSH 免密认证、Linux 硬件、Docker Engine 权限和远程主机到 Node Agent 回连地址的连通性。
5. 已登记主机可重新检测；指纹变化或检测失败时不得继续报告为可用。
6. Seed 镜像包含 OpenSSH 客户端，但不包含任何用户私钥或预置 `known_hosts`。
7. 阶段三 A 不宣称可以创建远程节点；该动作必须等待统一工作镜像和远程生命周期实现。
