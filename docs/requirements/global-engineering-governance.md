# 全局工程治理需求

## 目标

TaskHub 必须把本机全局开发规则与前端规则转化为可版本化、可执行、可审计的流水线约束，避免规则只存在于 Codex 会话或在项目收尾时集中治理。

## 范围

- 全局工程规则作为版本化生产对象保存，并且同时只能有一个生效版本。
- 新建项目合同自动绑定生效规则的不可变快照。
- 项目合同、执行计划、生产任务和编码上下文保留相同规则血缘。
- 每个执行批次完成代码集成后执行结构与治理门禁。
- 最终项目合同验收再次执行全量规则和质量命令。
- 项目级规则例外必须记录原因、风险、临时控制、恢复条件和到期时间，并经过明确批准；计划级和任务级例外在具备精确作用域校验前不开放。
- 规则升级不得改变已经运行或完成的计划；项目通过新合同版本迁移。

## 非目标

- 不让 TaskHub 直接修改受管项目源代码。
- 不把自然语言规则全部伪装成静态检查；无法自动验证的规则要求结构化人工证据。
- 不绕过现有 ProductSpec、ProjectContract、ExecutionPlan 和 EvidenceCenter 建立平行生命周期。

## 验收条件

1. 新项目合同包含规则 ID、版本、摘要、适用规则和编译后的执行指令。
2. 前端项目自动获得前端资料、400 行文件上限和多视口验证规则。
3. 执行计划和任务保留相同规则版本，编码节点收到规则指令。
4. 每个完成批次保存治理门禁摘要；失败或缺少人工证据时批次不得完成。
5. 新规则版本生效后，旧合同仍能验证其冻结快照，但预检提示建立合同修订。
6. 未绑定规则、摘要不一致或快照缺失时，项目预检阻止启动。
7. 只有有效、未过期且范围匹配的已批准例外可以把对应失败降级为警告。

## 回滚

代码回滚不会删除已保存的规则或例外对象。旧版本读取新增字段时使用空绑定默认值；重新启用治理后，未绑定合同必须通过合同修订迁移。
