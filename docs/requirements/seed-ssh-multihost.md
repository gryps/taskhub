# TaskHub Seed SSH 多主机节点编排需求

状态：SSH 准入、远程生命周期、镜像分发、逐节点凭据与期望状态协调 Alpha 已实现

版本：0.4

更新日期：2026-09-11

## 1. 目标

TaskHub 向用户提供两种业务镜像：种子控制节点镜像 `taskhub-seed` 和通用工作节点镜像 `taskhub-node`。用户手工部署并启动种子控制节点后，通过 Web 登记已经配置 SSH 免密登录的物理主机，并在指定主机上创建执行、测试、预生产等不同角色的工作节点。

目标方案不要求远程物理主机安装 TaskHub 宿主机 Agent。种子控制节点通过 SSH 管理远程 Docker；工作容器内部仍必须运行 TaskHub Node Agent，用于接收任务、报告健康状态和返回执行结果。

## 2. 产品边界

### 2.1 TaskHub 业务镜像

| 镜像 | 责任 |
| --- | --- |
| `taskhub-seed` | Web、API、LangGraph 编排、主机管理、节点调度、配置与状态持久化 |
| `taskhub-node` | 通用工作环境和 Node Agent；通过角色配置启用允许的工作负载 |

`taskhub-node` 是统一镜像。执行、测试和预生产角色不得因为工具组合不同而要求用户下载三个独立的 TaskHub 镜像。

PostgreSQL 等第三方基础设施镜像不计入“两种 TaskHub 业务镜像”。当前 Seed 使用独立 PostgreSQL 容器；如果产品要求用户总共只能下载两个镜像，必须另行决定改用内嵌数据库或将数据库打包进 Seed，并完成持久化、升级和恢复评审。

### 2.2 不属于本期范围

- 跨公网直接开放 SSH 或 Docker API。
- Kubernetes、Docker Swarm 等集群编排。
- 必须安装在远程主机上的常驻宿主机 Agent。
- Windows、macOS 原生任务执行；本期以支持 Docker 的 Linux 主机为首要目标。
- 在运行中的容器内动态切换角色。

## 3. 目标拓扑

```text
控制主机
└── taskhub-seed
    ├── Web / API / LangGraph
    ├── SSH 主机管理器
    ├── 节点调度器
    └── 状态数据库
          │
          ├── SSH → 主机 A
          │          └── taskhub-node (role=execution)
          ├── SSH → 主机 B
          │          └── taskhub-node (role=test)
          └── SSH → 主机 C
                     └── taskhub-node (role=preproduction)
```

单台远程物理主机允许运行一个或多个工作节点容器，也允许运行不同角色的容器。每个容器必须具有唯一节点 ID、独立运行配置和可单独限制的资源。

## 4. 用户前置条件

种子控制节点开始纳管远程主机前，用户负责完成：

1. 在控制主机上安装并启动 Docker。
2. 手工部署并启动 `taskhub-seed`。
3. 在每台远程主机上安装并启动 Docker 与 SSH 服务。
4. 配置从 Seed 运行环境到远程主机的 SSH 免密登录。
5. 确保 SSH 用户能够执行 Docker 命令，或具有受控的免密 `sudo` 权限。
6. 确保远程工作容器能够访问 Seed 的节点 API 地址。
7. 确保远程主机能够从配置的镜像仓库拉取 `taskhub-node`，或使用后续提供的离线镜像导入流程。

Seed 运行在容器中时，SSH 私钥、`known_hosts` 和网络路由必须在容器内部可用，不能只在宿主机终端中验证成功。

## 5. 核心用户流程

### 5.1 部署种子控制节点

用户通过发行包提供的 Compose 文件或安装脚本启动 Seed，并在 Web 首次访问时设置管理员密码。发布包不得包含开发者的密码、SSH 密钥、节点令牌、模型凭据或环境文件。

### 5.2 添加远程主机

用户在 **系统配置 → 物理主机** 中填写：

- 主机显示名称；
- IP 地址或可解析主机名；
- SSH 端口，默认 `22`；
- SSH 用户名；
- SSH 密钥引用；
- Docker 访问方式：用户直接访问或受控 `sudo`；
- 可选标签、用途和备注。

保存前，Seed 必须执行只读准入检测：

1. 建立 SSH 连接并验证主机指纹；
2. 验证免密认证；
3. 检测操作系统、CPU 架构、CPU、内存和可用磁盘；
4. 验证 Docker Engine 可用性和版本；
5. 验证 SSH 用户的 Docker 权限；
6. 验证目标主机支持 Seed 指定的工作节点镜像平台；
7. 验证目标主机到 Seed 节点 API 的网络连通性。

只有全部强制检查通过的主机才能进入“可用”状态。检测失败必须返回具体原因和修复建议，不得在创建节点时才首次暴露基础设施缺陷。

### 5.3 创建角色节点

用户在 **系统配置 → 节点容器** 中选择：

- 目标物理主机；
- 唯一节点 ID 和显示名称；
- 节点角色；
- 并发槽位；
- CPU、内存和磁盘限制；
- 数据目录或命名卷；
- 重启策略；
- 工作节点镜像版本。

确认后，Seed 通过 SSH 在目标主机完成：

1. 检查节点 ID 和容器名称冲突；
2. 拉取或确认存在指定版本的 `taskhub-node`；
3. 创建节点专用凭据，不向浏览器返回明文；
4. 创建数据卷和 TaskHub 管理标识；
5. 使用所选角色和资源限制创建容器；
6. 启动容器并等待健康检查；
7. 验证 Node Agent 已回连 Seed；
8. 将物理主机、容器和调度节点三者关联后显示为“可用”。

任一步失败时必须保留可诊断信息，并区分“未创建”“已创建未启动”“已启动未注册”和“健康”状态。重复提交同一创建请求不得产生重复容器。

### 5.4 生命周期管理

Web 至少支持：

- 查看远程容器、节点健康和资源占用；
- 启动、停止和重新启动；
- 查看受限长度的日志；
- 升级到指定工作节点镜像版本；
- 移除容器并注销调度节点；
- 明确选择保留或删除节点数据卷；
- 重新检测物理主机；
- 将失联主机标记为维护或停用。

Seed 只允许操作带有 TaskHub 管理标签且与库存记录匹配的容器，不得列出或操作主机上的其他业务容器。

## 6. 角色模型

`taskhub-node` 镜像包含标准工作环境，由容器启动参数确定角色。建议使用稳定枚举：

| 角色 | 允许注册的工作负载 | 主要用途 |
| --- | --- | --- |
| `execution` | `coding`、`build` | 开发、代码生成和构建 |
| `test` | `test`、`acceptance` | 自动化测试和验收 |
| `preproduction` | `build`、`test`、`acceptance` | 候选版本部署前验证 |

角色隔离不得只依赖前端隐藏按钮，至少必须同时落实在：

- 容器入口程序只启动角色需要的组件；
- Node Agent 只注册角色允许的工作负载；
- 控制节点调度器再次校验角色、能力和工具；
- 容器只获得该角色需要的凭据、挂载和网络权限；
- 容器使用非特权用户运行任务；
- CPU、内存、进程和磁盘资源受到限制。

角色变更通过重新创建容器完成，原数据卷是否复用必须由用户明确选择。

## 7. SSH 管理要求

### 7.1 认证

- 正式运行优先使用每台主机独立的 SSH 密钥，不以账号密码作为常驻认证方式。
- 私钥必须加密存储，禁止写入镜像、Git、日志或前端响应。
- 支持挂载已有私钥，后续可扩展由 TaskHub 生成并轮换主机专用密钥。
- 不允许直接使用 SSH `root` 账号作为默认方案。

### 7.2 主机身份

- 首次登记必须展示并确认 SSH 主机指纹。
- 指纹确认后写入受保护的 `known_hosts`。
- 禁止通过关闭 `StrictHostKeyChecking` 绕过身份校验。
- 主机指纹变化必须阻止自动操作并提示重新确认。

### 7.3 命令边界

- 优先调用参数化的 Docker 命令，不拼接未经校验的用户输入。
- 节点 ID、镜像、卷、路径和环境变量必须使用允许列表和严格格式校验。
- 命令超时、退出码、标准输出和标准错误必须结构化记录。
- 日志中必须脱敏令牌、私钥、密码和带凭据的 URL。
- SSH 重试必须有上限；网络不确定时先查询实际状态，再决定是否重试改变状态的命令。

## 8. 控制面与执行面责任

SSH 只负责远程 Docker 的部署和生命周期操作。任务执行不应依赖为每个任务临时建立 SSH 会话。

工作节点启动后，由容器内的 Node Agent：

- 主动向 Seed 注册；
- 报告角色、工具能力、槽位和健康状态；
- 接收经过调度的任务；
- 返回结构化执行结果和制品摘要；
- 在重连后按作业 ID 返回幂等结果。

控制节点继续持有权威 Git 仓库、LangGraph 检查点、任务状态、评审和发布权限。远程节点只能接收清理后的工作区，不得接收 `.git`、发布密钥或无关项目凭据。

## 9. 状态与数据模型

### 9.1 物理主机状态

建议状态：

```text
pending → checking → available
                    ↘ degraded
                    ↘ unreachable
                    ↘ disabled
```

每台主机至少记录：主机 ID、显示名称、地址、SSH 端口、用户名、认证引用、主机指纹、Docker 信息、资源摘要、允许承载的固定节点角色、标签、最近检测时间和状态原因。节点角色不得使用自由文本。

### 9.2 节点状态

容器状态和调度状态必须分开记录。一个容器处于 `running` 不等于 Node Agent 已注册或具备可调度能力。

每个节点至少记录：节点 ID、主机 ID、角色、镜像及摘要、容器 ID、卷、资源限制、期望状态、实际容器状态、Agent 健康状态、注册工作负载、最近心跳和最后错误。

### 9.3 期望状态协调

Seed 持久化用户要求的期望状态，并通过 SSH 查询实际状态进行协调。Seed 重启后必须能够恢复库存关系，不得因为内存状态丢失而重复创建节点。

当前协调器按平台心跳间隔在后台运行，并在每轮先按物理主机去重执行准入复检，再并发
协调该主机上的节点。节点使用确定性的容器名和命名卷：容器缺失时重建并复用原卷，
容器停止时按期望状态启动或保持停止，Agent 身份/健康检查失败时立即从调度注册表移除。
网络恢复且容器、Agent 再次一致后自动重新注册。每次协调时间、原因和最近 Agent 可见
时间写回持久化节点记录，浏览器只显示状态，不接收节点凭据。

### 9.4 逐节点凭据

Seed 为每个节点生成独立的高熵 Bearer 凭据，并使用部署配置加密根密钥加密后保存于
Seed 持久化配置卷。节点清单和 API 只保留版本、状态与不可逆指纹，不包含明文或密文。
调度器按目标节点 ID 解析对应凭据，不再回退使用部署级共享令牌。轮换会生成新凭据、
保留数据卷并重建目标容器；手动吊销会停止节点并退出调度，再次启动时签发新凭据；
删除节点会清除密文并标记吊销。旧版远程节点首次协调时自动生成独立凭据并重建容器，
从而完成迁移。

## 10. Web 交互要求

- “物理主机”和“节点容器”属于系统配置中的两个独立分组。
- 创建节点时，目标主机是必填项；默认可以选择 Seed 本机 Docker 主机。
- 主机选择项必须展示可用性、CPU/内存/磁盘摘要和连接错误。
- 角色名称、镜像版本和资源规格必须在确认操作前可见。
- 创建、启动、停止、升级和移除操作必须显示阶段性状态。
- 移除前必须确认，并明确数据卷和节点凭据的处理结果。
- 破坏性操作不得使用主按钮样式。
- 状态不能只通过颜色表达，错误必须包含可执行的修复建议。
- 窄屏允许资源表格内部横向滚动，不得产生页面级横向溢出。

## 11. 镜像分发与升级

- Seed 和工作节点镜像必须使用明确版本号，不得在正式环境依赖浮动的 `latest`。
- 创建节点时记录镜像内容摘要，防止同一标签指向不同内容而无法追溯。
- 同一主机创建多个角色节点时复用本地 `taskhub-node` 镜像层。
- 用户只创建某一种角色时，也只需要拉取统一工作节点镜像一次。
- 支持配置国内镜像代理和私有仓库。
- 离线环境应支持导出、校验并导入 Seed、工作节点及必要第三方基础镜像。
- 升级采用“拉取新版本、停止旧容器、以原配置重新创建、健康验证、失败回滚”的流程。

当前自动分发实现采用以下固定顺序：

1. 使用临时 Docker 凭据尝试私有镜像仓库前缀；
2. 尝试国内镜像代理前缀；
3. 尝试配置镜像的原始地址；
4. 网络拉取失败但目标主机已有同名镜像时使用缓存；
5. 仍无镜像时由 Seed 本机 Docker Engine 导出，通过严格主机指纹 SSH 输入远端
   `docker load`。

无论镜像来自何处，容器创建前均检查镜像操作系统、CPU 架构和内容摘要。使用
`name@sha256:digest` 固定镜像时，远端摘要必须与配置值一致；使用普通版本标签时，
系统记录本次实际解析到的仓库摘要或镜像 ID。SSH 兜底传输还会比较 Seed 与远端镜像
ID，避免传输后内容不一致。

## 12. 安全边界

- Seed Web 在可信内网之外必须使用 TLS 和安全 Cookie。
- 管理员登录、CSRF 防护和操作审计必须覆盖远程主机操作。
- SSH 用户拥有 Docker 权限通常等价于主机管理员权限，界面和文档必须明确提示。
- 节点凭据必须逐节点生成、可吊销、可轮换，并限制访问范围。
- 远程主机不得获得 Seed 的管理员令牌、数据库凭据和其他主机的 SSH 密钥。
- 容器不得默认使用特权模式、宿主网络或挂载 Docker Socket。
- 工作节点默认不发布宿主机端口；确有预生产访问需求时，通过项目级部署配置显式声明。
- 删除节点时必须撤销节点凭据；保留数据卷不代表保留访问权限。

## 13. 可靠性要求

- SSH 暂时不可用时，已经运行的工作节点继续通过 Node Agent 与 Seed 通信。
- Seed 暂时不可用时，工作节点不得自行执行未确认的新任务；恢复后重新注册。
- 创建、升级和移除操作必须幂等，并有唯一操作 ID。
- Seed 必须区分 SSH 连接故障、Docker 故障、镜像拉取故障、容器故障和 Agent 回连故障。
- 定期检测不得因为单台主机超时阻塞其他主机。
- 所有远程改变状态的操作必须保留操作者、目标、参数摘要、时间、结果和错误证据。

## 14. 验收标准

当前阶段已交付主机库存、指纹确认、私钥加密、准入检测、固定角色约束、统一
`taskhub-node` Alpha 镜像，以及远程创建、健康确认、启动、停止、重启和移除闭环。
升级回滚仍属于后续目标；逐节点凭据和自动协调已进入本版 Alpha。

### 14.1 主机准入

1. 能通过 Web 登记一台已配置 SSH 免密的 Linux Docker 主机。
2. 正确主机指纹确认后准入成功；指纹变化后自动操作被阻止。
3. SSH、Docker权限、磁盘或回连条件不满足时，准入失败并给出明确原因。
4. 密钥和敏感凭据不出现在 API 响应、日志、镜像和 Git 中。

### 14.2 节点创建

1. 用户能选择目标主机并分别创建 `execution`、`test` 和 `preproduction` 节点。
2. 容器实际创建在用户选择的远程物理主机，而不是默认创建在 Seed 主机。
3. 三种角色使用同一个指定摘要的 `taskhub-node` 镜像。
4. 节点只注册角色允许的工作负载，调度器拒绝不匹配任务。
5. 重复创建请求不会产生重复容器、重复卷或重复调度注册。
6. 容器健康且 Node Agent 回连后，Web 才显示节点为“可用”。

### 14.3 生命周期

1. Web 能远程启动、停止、重启、升级和移除受管节点。
2. 停止节点后保留注册关系和数据；节点不可再被调度。
3. 移除节点时注销调度记录、吊销凭据，并按用户选择保留或删除数据卷。
4. TaskHub 无法查看或操作远程主机上未带 TaskHub 管理标识的容器。
5. Seed 重启后能够从持久化库存恢复主机与节点关系。

### 14.4 分布式执行

1. 三台远程主机上的不同角色节点可同时在线。
2. 构建、测试和验收任务按角色与实际工具能力正确调度。
3. SSH 中断不影响已经注册节点的正常任务通信。
4. 远程节点不包含权威 Git 元数据、发布密钥或无关项目凭据。
5. 执行结果具备节点 ID、作业 ID、工作区摘要、退出码和制品摘要证据。

## 15. 当前实现差距

阶段三 B 第一版已能通过 Web 在已准入的 Linux Docker 主机创建并管理角色节点，
但统一 Alpha 镜像只包含 Python、Git、Node.js/npm、SSH 客户端和 Node Agent，尚未
包含 Codex CLI、浏览器及所有角色专用工具链。产品仍需完成：

1. 镜像升级、健康验证失败回滚和版本级数据卷迁移策略；
2. 创建前的远程端口冲突预检；
3. 完整浏览器及角色专用工具链镜像层；
