# 两段式初始化与项目激活

## 目标

首次使用必须明确区分平台全局准备和项目级开工约束，避免把特定项目的仓库、质量命令或
Windows 实机误报为 Seed 的全局前提。

## 第一段：Seed 基础设施初始化

Seed 初始化只检查管理员、Docker 与主机资源、访问与回连地址、工作节点镜像、模型服务和
首个本机工作节点。全部通过只表示“Seed 已具备接入项目条件”，不表示任意项目已经可以启动
开发。完成后提供进入项目激活的明确动作。

## 第二段：项目激活

创建或接入 Git 项目后，服务端按当前项目依次汇总：

1. 权威仓库及基准分支可访问；
2. 项目契约已核对并激活；
3. 契约中至少有一条真实可执行的质量命令；
4. 项目声明的验收依赖可用；
5. 项目预检全部通过。

验收资源是条件步骤。只有项目声明 `.taskhub/acceptance.yaml`、Windows 测试集或额外验收能力
时，才要求显式绑定项目获授权的节点。界面不得写死节点 ID 或主机地址；更换试点机只更新项目
质量配置。

项目契约的草稿和待批准版本允许编辑质量命令。契约生效后不可原地修改，必须创建修订版本。
编辑器以每行一条命令呈现，并由服务端解析为 argv，不通过 shell 执行输入文本。

## 状态与恢复

- `GET /api/projects/{project_id}/activation` 是项目激活页面的组合读模型；它复用项目预检、
  项目注册和项目契约权威，不复制事实来源。
- 激活状态始终按当前选中项目计算。一个项目的 Windows 或质量阻塞不得影响其他项目。
- 未完成时每一步都返回稳定修复目标；完成后主动作进入首个开发需求。
- 用户可以稍后处理，但开始流程按钮继续受项目预检约束，不能绕过门禁。

## 验收

- Seed 完成文案准确表达“可接入项目”，并可继续进入第二段。
- 接入项目后能看到五步激活状态、真实契约质量命令和下一修复动作。
- 声明 Windows 浏览器验收的项目显示节点绑定步骤；普通项目显示该步骤为按需且不阻塞。
- 1440、768 和 390 像素视口无页面级横向溢出，键盘焦点可到达编辑与修复入口。
